# 功能 GDD 三份产出契约（成稿 / 配置表 / 定稿）

`sr-gdd-human`（成稿）、`/sr-config`（配置表）与 `sr-gdd-ai`（定稿）是同一条链上的三步。本文件是三者分工、章节对应、两道门与退回方式的**唯一权威定义**——相关 skill 第 0 步一并读入，各自的 SKILL.md 只保留一行指针。改口径只改这里。

## 一、三份产出

| | 成稿（`sr-gdd-human`） | 配置表（`/sr-config`） | 定稿（`sr-gdd-ai`） |
| --- | --- | --- | --- |
| 定位 | 设计第一次落纸的**一次性中间产物** | 运行时配置数据 | **最终交付物，定稿后唯一的活文档** |
| 生命周期 | 定稿通过后**归档废弃**，不再维护 | 由 `/sr-config` 持续维护；**改表时同步定稿 §4 / §6 对应行** | 此后所有修改都落在这里（改动用 `sr-gdd-fix`） |
| 读者 | 审核人（策划 / 主策） | 程序、测试 | 程序、测试、配置 |
| 内容 | **只有纯规则**：功能意图、玩家动词、核心循环、功能规则、界面流程、范围门、埋点、验证计划、验收标准、交接清单、数值待定项；决策留痕在附录 A | 从成稿规则**派生**出的字段、结构、记录、数值 | 综合成稿规则与配置表落地的**整合稿**：功能规则、界面流程、§6 配置契约、§7 多语言文本、范围门、埋点、验收标准、交接清单 |
| 配置相关内容 | **零**——规则里不出现字段名、表名、"对应哪个字段"式中文字 | 全部 | 全部（§6 配置契约） |
| 多语言文本 | 无 | 无 | §7，据定稿列出**普通文本**条目 |
| 过程留痕 | 全部在这里（附录 A：来源、设计核、假设/风险台账、治理引用），随成稿一起归档 | — | 不带——定稿只写结果 |

**方向是规则优先**：`/sr-config` 从成稿的规则**派生**配置字段与记录——成稿的规则是配置表的唯一设计依据，规则写不清，字段就落不了地。

## 一·补·二　配置产物的落点（`/sr-config` 的产出）

配置表这条线的**人读产物一律落在功能目录**；配置目录（`config_root`）只放运行时真正要读的表。

| 产物 | 落点 | 说明 |
| --- | --- | --- |
| change set（`CS-<YYYYMMDD>-<NNN>.yaml`） | `<功能目录>\gdd\` | 人读交付物，与成稿 / 定稿同层（**不再写 `analysis\`**） |
| 读回验收报告（`*_读回验收报告.md`） | `<功能目录>\gdd\` | 同上 |
| **新建**的运行时表（`create_workbook`） | `<功能目录>\gdd\<表名>.xlsx` | **不直接写 `config_root`**；交付时必须明说「这张表还没进配置目录，需要你手动放过去」 |
| **改既有表**（`schema_change` / `record_change`） | `config_root` **就地更新** + 同目录 `<表名>.backup.<时间戳>` | 既有表是运行时在读的，不能搬进功能目录 |

**为什么这样切**：功能目录要能独立回答"这个功能产出了什么"（面板「最终产物 › 配置表」就是照这张表聚的）；
而运行时读的是 `config_root`，两份职责分开，谁也别替谁做主。**搬运由人做**——
`/sr-config` 只负责产出与验收，不偷偷往配置目录写新表。

**生命周期只有一次整合**：成稿把设计第一次落纸并留痕，定稿把成稿与配置表整合一次。**定稿通过后成稿归档废弃，定稿成为唯一的活文档**——设计微调、字段对应调整、文本改动都**直接改定稿**（涉及配置表时用 `/sr-config` 改表）。要不要再过一次定稿门，按改动大小由用户决定。

## 一·补　顶部状态元数据

两个 GDD 模板顶部带两个字段：**`doc_type` 管身份**（这份文档是成稿还是定稿），**`status` 管生命周期**（此刻处于哪一环）——一个字段只回答一个问题，不靠文件名后缀反推。

```yaml
---
doc_type: draft_gdd   # draft_gdd（成稿）| final_gdd（定稿）
status: draft         # 见下表，按 doc_type 分组取值
---
```

`doc_type` 与文件名后缀一一对应（`draft_gdd` ↔ 无后缀，`final_gdd` ↔ `_定稿`），后缀给人看，字段给流程读；两者不一致按 `doc_type` 为准并就地改正文件名。

**`status` 取值（按 `doc_type` 分组，各自身份的合法值封闭）**：

| doc_type | 合法 status | 流转 |
| --- | --- | --- |
| `draft_gdd`（成稿） | `draft` → `archived` | `draft`：撰写中、待成稿门或待修订。成稿门通过、定稿产出后置 `archived`。缺料阻断时也可为 `blocked`。 |
| `final_gdd`（定稿·主线路径） | `pending` → `active` | `pending`：整合已完成、待定稿审查与定稿门（审查发生在 `pending` 期，这是它的正常停留态）。门通过置 `active`。**定稿不再有 `archived`**——2026-10-12 起取消换版（`sr-gdd-fix`）：定稿永远同一个名字，历代样子由历史版本承担（见 `version-history.md`）。 |
| `final_gdd`（定稿·直接调用） | `provisional` / `blocked` | 未经成稿+配置主线，不能交程序；即使通过本次 Human Gate 也不升级 `active`。缺会改变决策的材料时 `blocked`。 |

通用规则：`blocked` 表示存在会改变设计决策的缺失材料或未解决阻断项（两类文档都可用）；要把 `provisional` 工作版升级为 `active`，必须补走 `sr-gdd-human → /sr-config → sr-gdd-ai` 主线。`sr-gdd-fix` 接 `status: active`（已生效）或 `pending`（定稿门之前的门内迭代）的定稿，`pending` 时它不代用户过门。旧文档没有头部字段时只能兼容读取和盘点，不能据文件名猜测主线可信度；用户明确确认它是当前有效定稿后，第一次由本系列保存时才补写两字段（`doc_type: final_gdd` + `status: active`）。

头部字段只描述文档身份与生命周期；阻断原因、来源、配置引用和决策关联继续写在现有决策记录、修订点清单与配置产物中，不扩展顶部 YAML。

## 二、首次定稿的章节对应

下表只在**从成稿生成定稿的那一次**用到；此后修改直接落在定稿上，不再对照此表。

| 成稿章 | 定稿章 | 整合方式 |
| --- | --- | --- |
| §1 功能意图 | §1 功能概述 + §2 本功能不解决什么 | 只取「一句话功能」那一段落到定稿 §1（**不拆子节**）；成稿 §1 的「本功能不解决什么」表落到定稿 §2；「为什么要做」只留成稿 |
| §2 玩家动词清单 | — | 只留在成稿，不进定稿 |
| §3 核心循环 | §3 | 同上 |
| §4 功能规则（R1、R2…） | §4 | 保留成稿规则与组号，把每条规则**对应到配置表里实际落地的字段/记录**——这是整合结果，不是另写一套规则 |
| §5 用户体验与界面流程 | §5 | 同上 |
| §6 范围门 | §8 | 同上 |
| §7 数据埋点信号 | §9 | 同上 |
| §8 验证计划 | — | 只留在成稿，不进定稿（原型阶段用，不属于程序交付） |
| §9 验收标准 | §10 | 同上 |
| §10 交接清单 | §11 | 按定稿角色重出 |
| §11 数值待定项 | §4 + §6 | 能在配置表里读到的标 `表名.字段名`，未落表的标"待配表" |
| §12 已废弃口径 | — | 只留在成稿（追溯用） |
| 附录 A 过程留痕 | — | 只留在成稿，不入定稿 |
| — | §6 配置契约 | 从配置表读回：**按工作簿分节**（`### 6.N`）+ 该工作簿的**表清单**（中文表名 / 输出名与映射名 / 索引 / **状态**）+ 每张表的**字段表**（中文字段 / 英文字段 / 结构 / 含义）；既有 key-value 表给键表；依赖的外部表单列一节。**状态在表级（已有 / 新增 / 新增命名待定 / 待配表），字段表与键表不带状态列** |
| — | §7 多语言文本 | 据定稿列出**普通文本**条目，**八列**（键 / 中文文案 / 占位符 / 状态 / UI位置 / UI状态 / 触发 / 用途；**键名未核验或未定的功能按模板增列 `候选Key名`**），与下游「正式 AI读版 · 多语言引用」逐列对齐；`状态` 取模板的**注册词表**（新增需求 / 修改需求 / 已提供Key-未核验 / 已核验Key / 建议复用 / 待分配Key / 本功能不再引用 / 待确认 / 不纳入AI读版）**不得自造**，`键` 列只放已核验官方键名或 `待分配Key`；表下必写**表级核验注**（文本源 + 条目数 + SHA256 + 核验结论），**没有核验证据不得写 `已核验Key`**；**文本表的增删改由用户自行发起**，定稿步不落表；GID 名称/描述键 `n{gid}`/`d{gid}` 随配置表 gid 走，不在此列 |

## 三、定稿门之前与两道 Human Gate 各批什么

- **定稿审查（仅主线路径，必经）**：`sr-gdd-ai` 第 5 步在定稿门之前调 `/sr-gdd-review` 出审查报告，报告随定稿一并呈门——审查是质量意见，不是通过凭证，`approve` 只能由用户批。直接调用路径（`provisional` / `blocked`）不审查。**成稿不设审查**（2026-10-13 定）：`draft_gdd` 不进本流程——成稿是中间产物，批它的是成稿门（批"设计与留痕"），`/sr-gdd-review` 的检查表是按定稿形态写的，套到成稿上有一半项目没有对应物。
- **成稿门（4 选项）**：批设计与留痕——规则、界面、范围、验收，以及附录 A 的假设与风险是否成立。
- **定稿门（5 选项）**：批**整合结果**——规则与配置字段的对应、§6 配置契约、§7 多语言文本是否可用，并参考审查报告。**通过即成稿生命周期结束**（归档）。

## 四、设计问题的处置（按成稿是否还活着分两种）

**定稿产出之前**（成稿仍是活文档）：`sr-gdd-ai` 发现规则 / 界面 / 范围 / 验收的设计问题，走**修订路由**退回 `sr-gdd-human`——出修订点清单 `<功能目录>\gdd\<主题>_<日期>_修订点.md`、本次任务状态置 `BLOCKED`，成稿修订后重新过自查与成稿门，规则变更后 `/sr-config` 重跑派生，再回来整合。配置落地问题（字段与规则对不上、数值缺失）则在定稿侧整合解决，必要时回 `/sr-config` 改表。

**定稿已产出、未过门**（`pending`）：属于**门内迭代**——由 `sr-gdd-ai` 直接改，或交给 `sr-gdd-fix`（`pending` 模式）承接；两者都按影响面闭合与最小编辑执行，`pending` 期间的任何改动都不构成过门（过门仍由定稿门批）。

**定稿通过之后**（成稿已归档）：**改动一律落在定稿上，由 `sr-gdd-fix` 承接**——它按撰写纪律做影响面闭合与最小编辑；涉及配置表时调 `/sr-config` 改表（改表后的定稿同步见它自己的第 5 步）；涉及文本时改 §7。`sr-gdd-ai` 只做首次整合，不再承接修改。

定稿缺**留痕信息**（证据编号、假设来源）：标"可选学习项"，不阻塞、不退回；过程留痕不在定稿中重建。

**直接调用路径**（只有旧案 / 配置表，没有成稿）：不适用修订路由；设计取舍按 `sr-gdd-ai` 第 2 步的决议问答向用户逐条拍板。

### 改完的复审按改动清单**分级**（2026-10-13 定）

**只用于「定稿通过之后」这一档**（由 `sr-gdd-fix` 承接的改动）；`pending` 的门内迭代**不分级** —— 它沿用 `sr-gdd-ai` 第 5 步的"改完复审"。

- **结构性改动** —— 改动清单里触及纪律文件「影响面闭合」条目所列**任一面**（规则 / 界面 UE / 范围门 / 埋点 / 验收标准 / §6 字段对应 / §7 多语言文本）⇒ **改完必调 `/sr-gdd-review` 全量复审**，报告与改动清单一并呈 `sr-gdd-fix` 的门。
- **轻量改动** —— 上列七面**一项都没被触及**（只动数值落地标注或文案措辞）⇒ **不跑全量**：走 `sr-gdd-fix` 第 5 步自查，并往**同一份**审查报告追加一节「改动后复核」（改动点 + 复核结论）。**没有可追加的报告时**（定稿从未过主线审查）按结构性处理 —— 顺手把报告建起来。
- **循环出口** —— `/sr-gdd-review` 只报告、不当场改；用户照报告裁决后再由 `sr-gdd-fix` 改的，**不再自动重审**：一次改动只自动触发一次复审，要再审由用户喊。

判据为什么用"改动清单"而不是"改了多大"：清单是 `sr-gdd-fix` 第 2 步就产出的、可核对的中间物，分级跟着它走就不用事后猜。
