# GDD 撰写纪律（成稿 / 定稿共用）

`sr-gdd-human`（写成稿）、`sr-gdd-fix`（改定稿）与 `sr-gdd-ai`（首次整合）共用同一套撰写纪律。**本文件是它的唯一出处**——条目编号（D1–D20）只在本文件存在，各 skill 只留指针，不复制条文、不引用编号；`sr-gdd-review` 作审查基准时同样按本文件核对。`适用` 列写明每条纪律落在哪一侧，变体不同的在条文里分开写。

| 编号 | 纪律 | 判据 | 适用 |
| --- | --- | --- | --- |
| D1 | **规则写法**：每条规则一句话说清"谁在什么条件下做什么、得到什么、边界是什么"，条件/动作/结果/边界齐全；一个主题一个规则组，只编组级 R1、R2…，组内不编小号；交叉引用引到组级（如"见 R2"），确需指明组内某条时写"R2 存量不足"这类"组号+规则名" | 非策划/程序的人能一句话复述；规则章只有组级编号 | 两者 · 定稿沿用既有组号，新增规则挂进所属组，出现新主题才新增组号 |
| D2 | **规则里只写设计语言**：成稿零配置指代——字段名、表名、`snake_case`、"对应某个字段 / 落到某个配置项 / 写进 XX 表"式中文字都不出现；定稿的规则正文同样只写设计语言，配置对应只写在 §4 的「配置字段」列与 §6 配置契约里 | 成稿：全文搜不到配置指代；定稿：规则列与「配置字段」列各归各位 | 两者 · 变体不同 |
| D3 | **数值**（状态词定义见同目录 `sr_project_context.md`「数值状态词」）：成稿写机制表述（"每 N 次""达到主城等级门槛""概率合计 100%"）+ 需落数处写"（参考值 X，待定）"，§11 只列待定项名称；定稿写实际落地 `表名.字段名`，未落表的标"待配表" | 成稿：把配置表数字任意改一遍，结果章一字不用改；定稿：每个数值都能在配置表里找到，或明确标"待配表" | 两者 · 变体不同 |
| D4 | **当前口径**：正文只写当前生效规则；被取代的旧口径在成稿收进 §12（一句话、不列表格、不做对比），定稿不放新旧对照——取代关系写进改动清单 | 正文无"曾经 / 原先 / 旧稿 / 变更前 / 本次已改"式表述 | 两者 |
| D5 | **界面章**：每个界面单独一张 ASCII 线框图（布局 + 控件 + UE 标注）+ 一张逐条编号的 UE 规则表；界面清单总览 + 流程 text 图 + 状态机（如适用）+ 全局交互规范；嵌套的解锁 / 失败分支 / 默认回退用层级缩进列表，不塞进大表格 | 每个界面都有线框图，注释单义、读不出第二种排版 | 两者 |
| D6 | **归属边界**：通用组件（如货币详情弹窗）与其它系统既有界面（如英雄详情页）在界面清单下声明"不属于本功能"，本功能只写触发关系 | 界面清单里每张图都能归属到本功能 | 两者 |
| D7 | **上游映射**：入口产出与旧案的每条设计结论落到对应章节——功能意图→§1；玩家动词→§2；核心循环→§3；功能详细→§4；界面/UE→§5；范围与不做项→§6；埋点→§7；验证计划（含**验证指标**与**测试后回写**）→§8；验收→§9；数值待定→§11；概念种子→A.2；设计核候选→A.3；玩家承诺→A.4；假设→A.5；风险→A.6；未决取舍→A.7；**不确定性校准→§4（随机性与概率类规则）+ §8（验证指标）**；迁移边界（sr-analysis 入口）→§4 规则 + §6 范围门。已拍板取舍直接成为规则口径，不重问、不写拍板过程；映射不了的差异写"待确认：<事项>"。§10 交接清单、§12 已废弃口径与 A.1 / A.8 / A.9 由成稿自产，不要求上游来源 | 上游每个设计结论在文中都有落点，不遗漏、不只在对话里提一句 | 仅成稿 |
| D8 | **证据纪律**（完整卡见 `evidence-boundary.md`）：证据优先级 `配置表 > 客户端代码 > 策划文档/UE > 推断`，材料冲突以高优先级来源为准、正文按胜出口径写；推断标 `【推断】`；市场 / 付费 / 增长类断言无证据不写入；缺材料时列最小缺失清单由人决定 | 每个推断有 `【推断】` 标记，无把未知写成确定事实 | 两者 · 定稿只用其中「轻量标注」一段 |
| D9 | **文本卫生**：术语全文一致（同一系统一个名字）；只留结构性留痕（表格、一句话条目），对话过程、中间草稿、被否掉的候选论证不进文档 | 术语无混用；无过程叙事 | 两者 |
| D10 | **附录 A 台账**：A.1–A.9 在成稿阶段随取舍同步填写（不事后补造）；无独立设计核取舍时 A.3 写"继承自入口产出"，不强凑 | 无占位符残留，与正文结论一致 | 仅成稿 |
| D11 | **影响面闭合**：改一处必须扫全受影响面——规则 ↔ 界面 UE ↔ 范围门 ↔ 埋点 ↔ 验收标准 ↔ §6 字段对应 ↔ §7 多语言文本；逐条列进改动清单，改完再核一遍 | 改动清单覆盖全部受影响章节；无"改了规则忘了验收 / 忘了字段"的漏改 | 仅定稿修改 |
| D12 | **模板形状即契约**：章节、子节与每张表的表列与形态基准**逐字一致**——定稿对 `../sr-gdd-ai/resources/templates/feature-gdd.md`，成稿对 `../sr-gdd-human/resources/` 的骨架；**不得增列、增节或改列名**。模板里带占位名的子节是**可重复模式，按实例数实例化**（`### R1 <规则组名>` → `R1`…`Rn`；`### 5.1 UI-M1 <界面名>` → `5.1`…`5.N`；`### 6.N <工作簿文件名>.xlsx（<角色>）` → `6.1`…`6.N`；`### 5.N 界面流程` / `### 5.N+1 状态机（如适用）` / `### 5.N+2 全局交互规范` 各最多一次）；**模板没有声明的章节或子节一律不通过 —— 这条按「任何层级的标题」执行：`####` 及更深同样不通过**（把一个界面/一张表的元素拆成小标题写＝越界，不是"补充说明"）。一个子节内部的元素细节写进**该子节的正文**（用 `**元素名**：` 行内加粗起头）、图注，或**既有表的单元格** —— **不新开标题**；**界面子节（§5.x）= 线框图 / 整屏图 1 张 + UE 表**（界面流程 / 状态机 / 全局交互规范各节同理：1 图 + 表或 text 图），界面元素与状态的细节写进**既有 UE 行的规则格** —— **不在正文另起段落把 UE 表里已写过的话再说一遍**（同一事实只写一处；与 §4 规则组、§10 验收标准同样不重复）。 | 章节序列与模板一致；每节表头列名逐字一致；**任何层级的标题都不得超出模板声明**（含 `####`）；子节只出现在模板声明的位置（占位模式按实例数实例化）；**界面子节图数 1 张**、元素细节在 UE 行内而不在正文重复 | 两者 |
| D13 | **组合边界**：凡规则引入**特殊态**（血量/数量按无限处理、数值为 0、空槽、达上限、唯一实例或互斥、跨周期与结算期、并发与离线、退盟或解散导致的归属变化），必须显式写出它与**每条相关规则**的交叉结果（例：血量按无限处理 ⇒ 依赖"剩余百分比"的提醒在该难度不触发）。成稿写完、定稿整合完各跑一遍"特殊态 × 规则组"扫描 | 任一特殊态与其余规则的交叉都有成文结论；无"两条规则各自正确、组合起来未定义"的格子 | 两者 |
| D14 | **执行语义成对闭合**：涉及消耗 / 获得 / 结算的操作，三者的**数量口径、扣发时点、失败与回滚处理**必须成对写全（只写一侧会让"是否需要反馈文案与结算呈现"无法判定）；公式、概率、阈值、例外与边界值必须给可执行口径，**不得以"按常规""沿用既有""参考同类功能"代替** | 消耗与获得 / 结算成对出现；公式与例外处无"按常规"式表述 | 两者 |
| D15 | **开放项必须带处理状态**（不得裸写"待定 / TBD / 待补"）：一律用统一标签 + **三件套**——**权威指针**（`表名.字段名` / 服务端字段）+ **当前值地位**（参考值 / 示意初值 / 待定档）+ **影响边界**（不改哪条规则语义）。标签词表：`【结构化源】` / `【后续补充】` / `【下游确认】` / `【待确认】` / `【本版本不做】` / `【占位】` / `【废弃】` / `【推断】`。**硬约束**：`【待确认】` 不得落在入口 / 解锁 / 状态转换 / 消耗 / 奖励 / 结算 / 限制 / 公式 / 异常 / 版本范围上——这些面要么定，要么明确"本版本不做"（裸留白与裸待确认都会变成下游的阻塞性追问）。标签与下游处理状态的对应见文末附注 | 全文搜不到裸的"待定 / TBD / 待补"；每个未定项能归入标签之一且三件套齐全；执行语义面上无 `【待确认】` | 两者 · 定稿更严 |
| D16 | **可见文案与文本键双向闭合**：§5 每个界面里出现的**玩家可见文案**，§7 必须有对应键，或在该处显式写"此处不需要文案"；反扫 §7 每个键在 §5 有落点。值待补时 `中文文案` 格写 `【占位：<待补内容>】`；占位符统一 `$n` 形式并在 `占位符` 列写 `$n＝<含义>（来源：<表名.字段名 / 服务端字段>）`、**可选占位符含义后标「（可选）」**；禁止 `N` / `X` / `【名称】` 等自由占位写法。界面状态按下游要求的类别逐类覆盖（可用/不可用、确认/取消、成功/失败、空/等待/冷却、奖励/消耗/结算），不适用的也要留一条结论 | §5 ↔ §7 双向对扫 0 缺口；占位符无自由写法；状态类别逐类有落点或"不适用"结论 | 两者 · 定稿必备 |
| D17 | **键名状态与核验证据**：§7 的 `键` 列**只放已核验的官方键名**；键名未定的写 `待分配Key`、建议名放进 `候选Key名` 列（该列为条件列：键名未核验/未定的功能必须增列，已全部核验的不增列）；`状态` 列取**注册词表**（新增需求 / 修改需求 / 已提供Key-未核验 / 已核验Key / 建议复用 / 待分配Key / 本功能不再引用 / 待确认 / 不纳入AI读版），**不得自造状态词**；键的落表与核验事实写进**表级核验注**（文本源文件 + 条目数 + SHA256 + 核验结论）——**没有核验证据不得写 `已核验Key`** | `键` 列无候选名；状态词全部来自注册词表；写了 `已核验Key` 的行能给出权威源与证据 | 仅定稿 |
| D18 | **配置字段必须写用途**：§6 字段表 / 键表的「含义」列写该字段**如何影响规则 / 状态 / 公式 / 显示 / 限制**，不得留空、不得写"待补字段说明"；依赖的外部表写清"引用它的什么、用在哪条规则上" | 字段表无空含义、无"待补"；每个字段能回答"它影响什么" | 仅定稿 |
| D19 | **权威边界与图片角色**：定稿头部说明块声明各类材料的权威关系——本定稿是设计语义默认来源；配置表 / 文本表在其自身领域内权威；图片与交互交付物是**证据与视觉参考**，含原型示意值的必须写明"图内数值、图标、文案为原型示意，落地口径以 §6 / §7 为准"。图片资产放功能目录下的固定位置并给清单；每张图在图注写 `界面ID + 状态`，并声明角色（正式界面证据 / 仅视觉参考 / 配置为权威） | 头部有权威边界声明；每张图有 ID + 状态 + 角色；示意图数值有声明 | 两者 · 定稿必备 |
| D20 | **排除项的两级粒度**：§2「本功能不解决什么」写**功能级排除项**（这项能力本功能不做 + 原因）；§8 范围门的"不做"行写**版本级范围**（本版本不纳入）。两者刻意不同粒度，**合并与去重反而丢信息** | §2 与 §8 的"不做"行各自有独立信息，不互为复述 | 两者 |

## 附注 · 标签与下游处理状态的对应（转 AI读版用）

定稿里的每个未定项，在下游「AI读版」流程里都会落到一个**处理状态**。下表让转置零判断：

| 定稿标签 | 下游处理状态 | 可出现的面 |
| --- | --- | --- |
| （无标签，正式口径） | 写入正式规则 | 执行语义 |
| `【结构化源】` | 引用结构化源 | 数值、表、键 |
| `【后续补充】` | 标记后续补充 | 数值定档、文案正文 |
| `【下游确认】` | 转下游确认 | 配置落地、派生链取数 |
| `【待确认】` | 标记待确认 | **仅限非执行语义** |
| `【本版本不做】` | 本版本不做 | 范围外 |
| `【占位】` | 标记待确认（值待补） | 文本值、资源 |
| `【废弃】` | 无关废弃 | 被取代的旧口径 |
| `【推断】` | 提出追问（应尽量避免） | 只在确无来源时 |

> 判据一句话：**每个信息点都能归入上表某一行**；归不进去的，下游会当成缺口处理（下游原话：`每个有效信息点都有处理状态`，否则即"影响执行语义且无处理状态"的缺口）。
