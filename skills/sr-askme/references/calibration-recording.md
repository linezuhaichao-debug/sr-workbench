# 校准记录方法卡（calibration-recording）

本卡定义「Human Gate 之前的用户迭代输入如何实时留痕」。它弥补的缺口：`decisions\决策记录.md` 里那条**人话**只说"定了什么"，而 Gate 前迭代循环里的来回取舍（谁提的、改了哪几处、消化了没有）需要一份**机器可查的流水**——会话中断即失忆，下游与复盘都拿不到过程。

## 谁在什么时候写（触发时机）

仅限**挂了本卡指针的 skill**（sr-concept / sr-analysis / sr-gdd-human / sr-gdd-ai），且仅在其**用户迭代循环**内：

| skill | 迭代循环位置 |
| --- | --- |
| sr-concept | 第 5 步：设计稿初稿出来后与用户迭代优化，直到认可 |
| sr-analysis | 第 6 步：复刻规格初稿出来后与用户迭代优化取舍，直到认可 |
| sr-gdd-human | 第 5 步：成稿呈现后用户提出修订/拍板，修改后再呈门的循环 |
| sr-gdd-ai | 第 6 步：向用户呈现定稿与审查报告后、与用户迭代优化的循环（含 revise；第 2/5 步自动分流与审查不产生用户输入，不写） |

指针插在各自迭代循环所在步骤——两个 GDD skill 的循环在 Gate 内部（revise），concept / analysis 的循环在 Gate 之前的独立迭代步，语义位置一致。此外：**Gate 选项回退到更早步骤产生的再迭代**（如 concept 的 merge_nuclei / regenerate_options 回第 2 步、analysis 的 request_more_evidence 回第 2 步）同样按本卡记录——回退路上用户给出的取舍也是拍板。

纪律：**用户每给出一次拍板/纠偏/选择，agent 先追加一条校准记录，再继续修改产出**——不允许"攒着最后一起写"。同一事项多轮确认不重复记（后一轮只补影响面变化时才追加）。

## 写在哪、写什么

- **路径**：`<功能目录>\evidence\calibration_<主题>.jsonl`（`<功能目录>` = `<SR_WORKSPACE>\features\<主题>\`；从策划工作台进来的会话里就是 cwd），append-only，一行一条 JSON。目录不存在直接创建。
- **单条格式**：

```json
{"ts":"2026-09-18T18:32:00","round":4,"gate":"成稿门","input":"旧配置全部废弃，删掉旧配置表并新建","affected":["OQ2","A4 台账","sr-config 建表方式"],"status":"applied"}
```

| 字段 | 含义 |
| --- | --- |
| `ts` | ISO 本地时间 |
| `round` | 本主题内的迭代轮次（从 1 递增） |
| `gate` | 当前门/循环名（如"设计核门""成稿门""定稿门"） |
| `input` | 用户拍板要点——抓关键句，不逐字记录原话 |
| `affected` | 受影响的章节/台账/规则组/下游 skill 动作 |
| `status` | `applied`＝已改进产出；`pending`＝已记录待消化（防"记了但漏改"） |

**粒度硬约束**：`input` 一句话、`affected` 最多 5 项、单条总长不超过两行——超了说明记的是论证不是要点。

## 与决策记录的区隔（重要）

校准 jsonl **不是决策记录**：决策记录是**给人读的时间线**（`decisions\决策记录.md`，一个功能只有一个文件，
条目 = 时间 + 决策内容，见 `decision-recording.md`）；校准流水是**机器留痕**，一行一条 JSON、给复盘与溯源用。
两者时机不同（迭代中 vs 每次拍板）、职责不同、互不替代 —— 校准流水**不往决策文件里搬内容**，
决策文件里那条人话才是权威结论。

## 每次拍板都写决策记录（v5 口径）

用户每给一次拍板 / 纠偏：

1. **追加一条决策记录**到 `<功能目录>\decisions\决策记录.md`（格式与落点见 `decision-recording.md`）——
   时间取当前本地时间到秒，正文写 `**决策**：` / `**依据**：` / `**影响**：`；
2. 如果这次拍板发生在本卡覆盖的迭代循环里，**同时**往校准 jsonl 追加一行流水（要点 + 影响面 + status）。

两者一起写、各写各的形态：决策记录给人读，校准流水给机器查。**不要**再把校准内容汇总进某个
`decision_result.calibrations` —— `decision_*.json` 那份格式已废弃（见 `decision-recording.md` 第一节）。

## 归档（可选）

一个主题的 Gate 走完、不再迭代时，可把 `calibration_<主题>.jsonl` 就地改名为
`calibration_<主题>_<日期>_归档.jsonl` 以区分"当前这一轮"与"上一轮"。**纯属整理，不影响任何判据**；
不归档也不会出错（下次迭代接着往同一个文件追加即可）。

## 会话恢复纪律

接手中途会话（新会话续做、上下文压缩后继续）时：先读本主题校准 jsonl 的尾部若干条，核对 `pending` 项是否已消化——有 pending 先消化再继续流程，防止"记录了但产出没改"。

## 不适用

- 未挂本卡指针的 skill 不写校准记录（无迭代循环的 skill、纯工具 skill、已有自身留痕机制的 sr-gdd-fix 用 changes、sr-config 用 change set）；
- 不逐字记录用户原话、不做产出快照哈希——要点 + 影响面已够复盘与溯源，避免写入负担压垮纪律本身。
