# 四类判定口径与证据纪律

## 一、怎么定档

### 未实现
定稿要求的**可观察行为**在代码里找不到承载。

成立的样子：
- 预制件有节点、有文案位，但 Lua 全篇没有引用该节点（`grep` 节点名 0 命中）。
- 全仓 `grep` 关键能力（渠道号、页签类型、函数名）0 命中。
- 入口没有接线：菜单/建筑/页签存在，但点击不进入目标页面。

不成立的样子：
- 代码里有但被注释掉 —— 先 `grep` 全仓确认没有别的实现接手，再定。
- 只在某分支下走不到 —— 那是「实现错误」或「不确定」，不是没有。

### 实现错误
做了，但**取值、文案、条件或状态**与定稿相反或不符。

典型：
- 取错字段（该用技能战力却取了升星战力）。
- 用错文本键（空槽按钮用「穿戴」，定稿是「装备」）。
- 条件写少一条（无英雄槽位仍点亮锁图标）。
- 少一个状态（指示点只有实心、没有空心）。
- 路径被拦在半路（候选为空直接 toast，永远进不了本该承载空态的页面）。
- 请求期间禁用按钮，而定稿明确「不置灰、不防连点」。

### Bug
代码本身有缺陷，不改需求口径也会出错。

典型：
- 赋值给局部变量（`textComp = ""`），没写回控件。
- 每次刷新重复 `SetLua` 包层，状态不干净。
- 两处对同一状态判定不一致（一个过滤了「已激活」，一个没过滤）。
- 空循环体、死代码，掩盖了本该做的初始化。
- 状态记了但从不消费（`self.side` 只赋值，渲染从不读）。

### 不确定
依赖仓库外的事实，或定稿自相矛盾。

必须写成「不确定」的：
- 服务端规则（保底、事务、结算、技能实际生效、属性入战力）而服务端不在工作区。
- 预制件静态文案、贴图颜色、动效是否内建 —— 只能靠节点树猜。
- 定稿两条口径冲突（例：返回一律回装备页 vs 建筑入口不依赖英雄）。
- 配置值本身是测试值，只有口径缺字段（如「比例格式待配表」）。
- 需要实机验证的（滚动位置是否保留、按钮是否可重复点）。

每条「不确定」必须写 **怎么才能确认**（看哪个文件、跑哪个场景、问谁）。

## 二、证据纪律

- 一条问题一条定位：`文件:行号`（多行写 `:88-97`），或 `文件:函数名`。
- 引定稿原文时保留**完整判断条件**，不要只摘半句（半句会让用户没法核）。
- 判「已通过」也要给证据：说明哪段代码满足哪条口径，否则不写。
- 结论先写「现状」，再写「影响」，不要先写判断词（「违反了」放影响里）。

## 三、常见误判清单（踩过）

| 误判 | 实情 | 正确写法 |
| --- | --- | --- |
| 看到关键字 0 命中就判「未实现」 | 可能被别的前缀/聚合层包了 | 换 2–3 种说法再 grep，含拼音缩写与英文别名 |
| 节点在 = 功能在 | 节点常是设计稿残留 | 必须找到 Lua 对该节点的引用 |
| 文案缺失 | prefab 可能静态写死中文 | 落「不确定」，验收动作写「切语言看是否跟随」 |
| 数值看着不对 | 配置是测试值 | 定稿标了「测试值/待配表」→ 不确定 |
| 服务端没做 | 只是不在本仓 | 不确定，并在页面挂上对应需求编号 |
| 把定稿自相矛盾判成实现错误 | 两条口径都可能对 | 不确定 + 列出两条原文，交用户裁决 |

## 四、严重度

- **高**：玩家可见的功能点缺失，或口径相反会算错（战力取错、状态判错）。
- **中**：表现缺失、文案错、链路被拦，用户能感知但不至于算错。
- **低**：实现质量、格式、待裁决小项。
