# 实现核查：需求 → 代码 → 可勾验的对照台账

一句话：**每个问题旁边必须放上它违反的那条需求原文**，否则结论不可核验。
界面问题还要多一条：**旁边放上效果图与实机截图的并排标注**，否则「长得不对」也只是主观说法。

## 交付物（四件，同一版本目录）

| 文件 | 作用 |
| --- | --- |
| `圣物系统_需求清单_v1.0.md` | 把定稿拆成可判定条目（R1-1、M3-3 这样的编号），核查基线 |
| `圣物系统_实现核查报告_v1.0.md` | 按类别分档的明细，每条带 `文件:行号` 证据 |
| `UI对照/` | 收图说明 + 工程截图 + `标注/` 下的标注图（每张只标一类问题）。**仅第 0.2 步选了「做 UI 核对」时才产出** |
| `圣物系统_核查对照_v1.0.html` | 左问题右需求的双栏台账，可勾选核验、写备注、按类别筛；界面问题内嵌标注图 |

后三件都以第一件的编号为准；全部标 `doc_type: derived`，**不是策划交付物**。

## 第 0 步（必做）：先问要核哪个包

不要自己猜需求包，也不要默认用上一次的。先跑清单脚本，把结果摆给用户挑：

```bash
node "<SKILL_DIR>/scripts/list-packages.mjs"
```

- `<SKILL_DIR>` 是本文件所在目录。真源在 `D:\TimeMachine\sr-workbench\skills\sr-impl-check`（策划工作台的「其他技能」）；`C:\Users\ZuHaiChao\.agents\skills\sr-impl-check` 是指向它的 junction，两个路径都可用。
- 可用 `--root "<其他 下游包 目录>"` 指向别处；也可 `--json` 取机器可读结果。
- 输出里 `[定稿?]` 是需求正文，`[说明]` 是交付说明，派生材料（核查/清单/报告）已自动过滤。

然后用 `ask_user_question` 让用户确认两件事（可以合成一个问题，选项里带上包名+版本）：

1. 核哪个包 / 版本；
2. 该目录里哪份文件是定稿需求正文（通常 `AI读版策划案_*.md`；若有多个，让用户点一个）。

用户直接给了路径时跳过提问，但仍要确认那份文件是定稿而不是草稿。

### 0.2 问一句：这轮做不做 UI 核对（必须问，且只问一次）

选完包、确认完定稿之后，**紧接着**用 `ask_user_question` 问一件事：**这轮要不要做 UI 外观核对**。两个分支走到底，不来回改口：

- **选「否」→ 只做代码审查验收。** 跳过第 5 步全部内容，**不建 `UI对照/`**，报告不出「UI 外观偏差」一节，交付物只出需求清单 + 报告 + 对照页三件；后面所有环节**不再提截图**。
- **选「是」→ 当场把收图清单交出去**，不要等代码核完、不要拖到第 5 步：
  1. 建 `<版本>/UI对照/`，下分 `工程截图/`、`标注/`；
  2. 按 `assets/ui-capture-checklist.md` 模板写 `<版本>/UI对照/_收图说明.md` —— **扫一遍 `UI效果图/`，把每个语义名都列进配对表**；同版式只换配色的多状态弹窗（如四品质详情）合并成一行、只截一张；
  3. 在回复正文里**把配对表贴出来**（不要只说「文件写好了，你去看」），并交代四条要求与放图位置；
  4. 然后**立刻转入第 1 步继续核代码** —— 用户截图与代码核查并行，互不阻塞。

> 为什么必须当场给：用户一答应做 UI 核对，他要做的下一件事就是去截图。清单晚一步交，他就只能干等。把这一步留到第 5 步才做，是本 skill 最常犯的错。

用户已经明说「这次只看代码」「不核 UI」的，视为选了「否」，**不要再复述确认**。版本目录里没有 `UI效果图/` 时，照问，但把「没有效果图，选了也没有对照基准」写进选项描述里。

## 第 1 步：读定稿，抽需求条目

- 通读全文。**先只抽「要发生什么」，不写实现结论**，避免被代码带偏。
- 编号规则（沿用本仓习惯，让报告和 HTML 能互相引用）：
  - `R<章节号>-<行号>` 功能规则（R1-1 … R12-3）
  - `M<界面号>-<UE号>` 界面条目（M1-1 … M12-4）
  - `G-<n>` 全局交互规范
  - `CFG-<n>` 配置与外部依赖，`TXT-<n>` 多语言文本，`QA-<n>` 评审答复，`ART-<n>` 美术资源
- 一条规则里如果并列了多个可独立判定的动作，拆开（例如「装配/替换/卸下各自要刷新什么」）。
- 写完自查：定稿里的每张表、每段 UE 是否都有对应编号；有没有把「不解决什么」误当需求。

产出 `*_需求清单_v1.0.md`：每节一张 `编号 | 需求点 | 判定要点` 表。

## 第 2 步：定位工程与代码簇

默认工程根 `<workspace>/PlanetRoot`（Unity + Lua 热更，Lua 脚本是 `Assets/HotRes/Lua/**/*.txt`）。用户会给别的工程时以用户为准。

按「先入口、后主体」找代码：

1. 用定稿里的**专有名词**（系统名、界面名、文本键前缀）grep 出入口：菜单/建筑/商店页签/道具引导渠道。
2. 顺着入口找到 UI 目录、数据层、协议层：`grep -l "前缀" --include=*.txt`。
3. 再看**配置是否已落运行时表**：`Assets/HotRes/Lua/LuaConfigs/`（生成物）与 `LuaConfigs/View/`（读表类）。
4. 把代码簇按「数据 / 配置访问 / 各界面 / 组件 / 入口接线」列出来，估算行数，再决定自己读还是分工。

小工程（几千行）自己全读；大工程按界面分给子代理，但**编号与判定口径必须由你统一**。

## 第 3 步：逐条核查，四类定档

| 类别 | 判定标准 | 典型证据 |
| --- | --- | --- |
| 未实现 | 定稿要求的可观察行为在代码里找不到承载 | 节点存在但无脚本引用；全仓 grep 关键字 0 命中；入口没有接线 |
| 实现错误 | 做了，但取值/文案/条件与定稿相反或不符 | 取错字段、用错文本键、条件写反、少一个状态 |
| Bug | 代码本身有缺陷，会直接出错或状态不一致 | 赋值给局部变量、重复绑定、两处判定不一致、死循环体 |
| 不确定 | 依赖仓库外的事实（服务端、prefab 静态文本、美术资源）或定稿自相矛盾 | 服务端 RPC、预制件文本、图标颜色、两条口径冲突 |

纪律：

- **一条问题一条证据**：`文件:行号` 或 `文件:函数名`。只写「可能」「大概」的不要进前三类，放「不确定」并写清怎么才能确认。
- 服务端不在工作区时，**不要**把服务端规则判成「未实现」；统一写「不确定（无代码可核）」并在对照页里挂上对应需求编号。
- 判断「注释掉了」「节点在但没接线」时，先全仓 grep 关键词，确认没有别的脚本接手。
- prefab 里可能的静态文案、贴图颜色：可以读 `_node_tree_dump.md` 之类节点树辅助，但结论放「不确定」。
- 已核对通过的条目也要单列（`P1…Pn`），每条带需求编号——证明覆盖到了，而不是只列坏的。

报告结构固定：`0 口径 → 1 未实现 → 2 实现错误 → 3 Bug → 4 不确定 → 5 已通过（抽样）→ 6 处理顺序`。

## 第 4 步：配置与文本

- 生成物能直接统计：行数、gid 区间、`star=0 的 cost` 是否等于 `combinePiece`、`unlock` 是否 5 的倍数、概率合计是否 100%。
- 文本键：拿定稿 §7 的键表去 `Locale/string_zh_CN.txt` 逐个查，缺哪些、哪些缺 `$0` 占位符，都是硬结论。
- 配置问题写在「不确 定」还是「实现错误」取决于定稿是否给了口径：口径明确却配错＝实现错误；口径本身就是测试值＝不确定。

## 第 5 步：UI 效果图核对（仅第 0.2 步选了「是」才执行）

**选了「否」的，整节跳过。**

> **收到图 = 交付信号。** 从图到手那一刻起不再向用户提问，一气做完「自验 → 逐张读图 → 记清单 → 批量出图 → 自检 → 写报告 → 出对照页」。唯一例外是定稿自相矛盾、只能由策划裁决的问题。

代码核查回答「有没有做」，这一步回答「长得对不对」。完整规程见 `references/ui-diff-guide.md`。

### 5.1 四条原始约束（本步的验收线，一条都不许折扣）

这是用户交办这个任务时的原话，逐条照做：

1. 把截图里**与效果图不一致**的地方标注出来；
2. **每张标注图只标一类问题**；
3. 效果图里**有**而工程里**没有**的，也要告诉他；
4. 工程里由代码生成的内容（列表条目、数量、星级、数值、选中态）不一样属正常，看的只是 **UI 样式**；
   效果图里的 `Confirm`、「文本内容描述」「属性巴拉巴拉」是设计稿占位，不当差异报。

> **本步基准是效果图，不是定稿。** 定稿与效果图冲突的照样报，在标注里注明「定稿口径不同，待裁决」。
> 把「定稿优先、效果图过时」那套搬进这一步，会把本该报的差异主动吞掉 —— 这是最常见的偏移。

### 5.2 看图：逐张读原图，禁止用拼接图代替

- 每一屏读**两张**：效果图一张、工程截图一张。**屏数 × 2 就是 read_image 的最低次数。**
- 结构有疑点时再放大读一次看细节（角标、叠字、层级、边框）。实战量级：14 屏 ≈ 41 次读图。
- **禁止**把两张图拼成一张再读 —— 拼接后细节被压掉，等于没看。拼接图只用于出图，不能用于看图。
- **先把所有屏看完、把差异清单记全，再开始出图。** 边看边出会漏掉后半段的关联问题。
- 同版式只换配色的多状态弹窗（如四品质详情）读一张代表即可，其余复用同一结论 —— 这是唯一允许的省读。

> **别拿上下文当借口。** 100 万窗口下 41 次读图最终只占约 25%。读图不贵；没看图就下结论才贵。

### 5.3 出图：一处差异一张，同一类跨屏也各出一张

- **一条差异 = 一张标注图。** 14 屏出到 30–40 张是**正常量级**，不是异常。
- 「每张图只标一类问题」说的是**一张图不混标两类**，**不是**「一类问题只能出一张图」：
  三个页签的文案错 → 三张图（或一张图里多组区域），**不能压成一张「文案差异」**。
- **禁止**为「出图省事」合并条目。现成脚本的 `regions` 一次装不下二三十条，就分批跑或另写循环，
  **不许减数量**。
- 效果图有、工程没有的元素单独成图（缺失元素），不要塞进别的图里顺带一提。

### 5.4 自检：出完必做，一件都不能省

1. **缩略图体检**：把全部标注图缩成一张总览，一眼扫有没有「取歪了」（框在空白、左右取反、标错元素）。
2. **数量对账**：差异清单条数 == 标注图张数。对不上就是有合并或遗漏。
3. **抽样复读**：随机挑 2–3 张对照原图，确认框住的正是那处差异。

出图途中两类返工，遇到就修完再继续：脚本左右取反（两张都取了效果图）、caption 超宽被裁。

### 5.6 其余纪律

- **找图**：扫版本目录下名字带「效果图 / UI图 / 设计稿」的目录；同一张图常有语义名与 `IMG-00x__`
  两套文件名，按文件大小去重，用语义名做配对键。
- **目录与清单应在第 0.2 步就已建好交出**；若漏了补建，并把配对表贴进正文，别只丢文件路径。
- **收图自验，不回头问**：核对文件名/分辨率/缺哪几张。缺图不阻塞交付 —— 缺的屏记「未收到截图」
  或「工程该屏打不开」，照常出标注图、报告与对照页；补图后重渲染即可（`extract-check-data` →
  改 → 重渲染，slug 不变，勾选与备注不丢）。
- **比对顺序**：先结构（区块顺序、缺块）→ 元素（在不在、位置对否）→ 样式（角标/底色/字号/对齐/层级）
  → 文案。
- **分类六档**：多余元素 / 缺失元素 / 样式差异 / 布局差异 / 文案差异 / 状态差异。
- **裁判**：拿不准标「待确认」并写清两种可能，不替策划选。
- 界面问题在报告里单列一节「UI 外观偏差」，与代码四类分开统计，编号续用 `U<n>`。

## 第 6 步：出对照页

先写一份 JSON（格式见 `node "<SKILL_DIR>/scripts/build-check-page.mjs" --print-schema`），再渲染：

```bash
node "<SKILL_DIR>/scripts/build-check-page.mjs" \
  --data "D:\...\relic-check.json" \
  --out  "D:\...\圣物系统_核查对照_v1.0.html"
```

脚本会做自检：类别非法、缺 id/标题/证据/需求、编号在需求清单里找不到、标注图读不到，都会报出来。**有 warning 先补齐再交付**——尤其「需求编号在清单里找不到」，通常意味着清单漏条或编号写错。

界面问题把标注图挂到 `shots` 上，渲染时自动内嵌，页面仍是单文件离线可开：

```json
"shots": [{ "src": "…/UI对照/标注/C1_圣物抽卡_缺失元素_跳过动画.png",
            "caption": "效果图有勾选（绿框），工程该位置为空（红框）" }]
```

图片先压到宽 1000px 左右；自检会打印「标注图：N 张，已内嵌 X MB」，超 16 MB 会给 warning。

> 版式已固化在 `assets/page-template.html` —— 就是当初用 `/html` 设计并逐屏验收过的那一版，已改成数据驱动。**跑这个 skill 不需要 `/html`**：同一份数据重渲染，版式与交互完全一致。只有要换视觉方向，或要图表 / 多页这类新形态时，才用 `/html`（或 `design-artifact`）重新设计模板、替换该文件。

写 JSON 的硬要求：

- 每个 `issue.reqs` 至少 1 条，是 `["编号", "定稿原文（可截取关键句，保留完整判断条件）"]`。
- `check` 写成**可观察的验收动作**（「关闭 531 后进装配页，冒险槽出现锁图标」），不要写「符合需求」。
- `spec` 按 A/B/C/D/E 分节，每节 `["节标题", "编号|一句话\n编号|一句话"]`；编号必须和报告一致。
- `sev` 用 高/中/低，帮用户排处理顺序。

把已有的页面改一条（或只想重新渲染）时，先从页面把数据取回来，别手抄：

```bash
node "<SKILL_DIR>/scripts/extract-check-data.mjs" --from "D:\...\圣物系统_核查对照_v1.0.html" --out check.json
```

数据内嵌在页面的 `window.__CHECK_DATA__` 里；取回 → 改 → 重渲染，**slug 不变**则用户的勾选与备注照旧有效。

渲染后自检（有浏览器就截图，没有就至少跑 `--check`）：

```bash
node "<SKILL_DIR>/scripts/build-check-page.mjs" --data check.json --check
```

## 交付

1. 三件文件放进 `<下游包>/<需求>/<版本>/`，与需求正文同目录；第 0.2 步选了「做 UI 核对」时多带一个 `UI对照/` 目录（选「否」则不建、不提）。
2. 页面的「已核验」勾选与备注存在本机 localStorage（键 `slug + '-v1'`），换机器不跟随文件——交付时说明一句。
3. 需要留痕时，往需求库 `.process/log/YYYY-MM-DD.md` 追一条：包名、版本、核查范围、各类计数、是否改了代码（应始终为「未改动」）。
4. 报告末尾给处理顺序：口径错的先改（低成本高感知）→ 补缺 → 修 bug → 对齐文本与配置 → 待裁决项；界面偏差单列一节，按「缺失 > 布局 > 样式 > 文案」排。
5. **图到手就一次交完**：需求清单 / 报告 / 标注图 / 对照页在同一轮全部落地。不要先交报告、再等一句确认、然后才出页面。

- `references/example-check.json` — 可跑通的最小样例：`--data` 喂它即可验证链路。
- `scripts/annotate-ui-diff.py` — 效果图/工程截图并排标注出图器；`--print-schema` 看数据格式。
- 依赖：Node 20+（页面脚本只用内置模块）；UI 标注额外要 Python + Pillow（`python -m pip install pillow`）与一个中文字体（Windows 自带微软雅黑即可）。

## 边界

- 只读需求正文与工程代码，**不改**策划案、配置表、代码。
- 不把实施事实（节点名、接口字段、代码路径）写回需求文档。
- 定稿自相矛盾时，列进「不确定」并写清两条口径，交用户裁决，不要替策划选。
- 工程截图由用户提供，**不替用户操作编辑器**；只在用户已经把图放进来之后做对比与标注。
- UI 偏差以效果图为准，但效果图占位文案（`Confirm`、「文本内容描述」）不作为工程文案问题的依据。
