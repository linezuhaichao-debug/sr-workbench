# 功能 GDD 定稿审查工作流（SR-GDD-Review）

## 功能说明

**唯一输出：审查报告**。对 sr-gdd 系列产出的功能 GDD **定稿**做只读审查——结构骨架、撰写纪律、数值落地标注、配置契约与多语言文本、与成稿/配置表的整合一致性——落在 `<功能目录>\gdd\<主题>_<日期>_审查.md`，供用户决定是否交程序。

- **只读，不改定稿**：管线里对定稿的改动统一由 `sr-gdd-fix` 承接（最小编辑 + 影响面闭合 + 决策记录，见 `../sr-askme/references/gdd-pipeline.md`），审查只负责发现问题并把证据写足，让修复能照单执行。用户确认修复后转 `/sr-gdd-fix`，不在本 skill 内动笔。
- **分层审查**：基础自检（V1–V9，定稿本体的写作纪律）+ 整合一致性（V10–V14，与成稿/配置表/界面素材交叉核对）。整合层缺对照物（无成稿、无配置表或无界面素材）时只做能做的部分，缺什么在报告里写明"未核"，不算不通过。
- **不做设计改判**：规则好不好玩、数值合不合理不是审查对象；本 skill 查的是"这稿是否可交程序实现"。设计矛盾类发现只定位证据、交用户裁决。
- **不替定稿门背书**：定稿门（`approve`）只能由用户批；审查报告是质量意见，不是通过凭证。

## 使用方法

```
/sr-gdd-review <定稿路径或主题>
```

或直接说人话，例如"审查一下神话宝库的定稿"、"这份 GDD 能不能交给程序"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **定稿**：路径或主题（只给主题时在**本功能目录的 `gdd\`** 下定位；多份候选项列给用户选，不默认取最新）。没有定稿时停止，说明应先走 `/sr-gdd-ai`。
2. **对照物**（有就给路径，没有就明说没有；不影响开工，只影响整合层覆盖度）：对应成稿、配置表（.xlsx 或 `/sr-config` 产出记录）、相关决策记录。

## 路径约定

`<SR_WORKSPACE>` / `<SR_PROJECT>` 取自 `%USERPROFILE%\.dsh\sr-workbench\config.local.json`；字段缺失、为空或路径失效时运行 `/sr-askme` 补齐；成组安装见 `../sr-askme/SKILL.md` §四。

产出落**本功能的目录**（`features\<主题>\`）：审查报告进 `gdd\<主题>_<日期>_审查.md`。
本 skill **只读、不改定稿**，但审查结论同样是决策（「这份定稿能不能交程序」就是这么一条）：
- 决策记录：**只要定下了一件事就记**（选组件 / 定布局 / 定交互 / 放弃某个方案 / 更正之前的判断…，不只 Human Gate 那一次）。落点与格式见 `../sr-askme/references/decision-recording.md` —— 追加进**本功能**的 `decisions\决策记录.md`（一个功能只有一个决策文件）。

## 执行流程

### 第 0 步 · 前置分诊

读定稿顶部 `doc_type` + `status`（两字段定义见 `gdd-pipeline.md` §一·补），按表分流：

| doc_type | status | 处置 |
| --- | --- | --- |
| `final_gdd` | `pending` | 主线首次定稿待审查——ai 第 5 步的常规到达形态，全量审查。 |
| `final_gdd` | `active` | 当前生效定稿——独立调用，或 `sr-gdd-fix` 做完**结构性改动**后的必调复审（**轻量改动不进这里**：由 `sr-gdd-fix` 往同一份报告追加「改动后复核」，口径见 `gdd-pipeline.md` §四）；全量审查；已有审查报告且此后未再改动时先问是否重跑。 |
| `final_gdd` | `provisional` / `blocked` | 照常审查，但报告开头注明"非主线 active 定稿，不能直接交程序；升级须补走 `sr-gdd-human → /sr-config → sr-gdd-ai` 主线"。 |
| `final_gdd` | `archived` | **仅历史遗留文件**（2026-10-12 取消换版后不再产生）：已被替代或废弃，不审查；请用户指认当前生效定稿。 |
| `draft_gdd` | 任意 | 不在本 skill 范围：**成稿不设审查**（`gdd-pipeline.md` §三），批它的是成稿门（`sr-gdd-human` 第 5 步），提示用户走那道门；用户坚持时才按本清单中适用成稿的项审查（V10–V13 在成稿上无对应物，逐项标"不适用"），并在报告注明审查口径。 |
| 无头部字段 | — | 请用户确认是否当前有效定稿；确认后照常审查，报告中注明"按用户确认视为定稿"。 |

完成判据：已读两字段并按表确定本次审查口径（pending 全量 / active 复审询问 / 非主线注明 / 成稿转介 / 用户确认旧文档）。

### 第 1 步 · 载入项目语境与撰写纪律

读 `../sr-askme/references/sr_project_context.md`（数值状态词）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与章节对应表）、`../sr-askme/references/gdd-writing-discipline.md`（撰写纪律，取定稿侧适用项作审查基准）、`../sr-askme/references/evidence-boundary.md`（只用「轻量标注」一段）。

本 skill **只读、不改定稿**，但审查结论同样是决策（「这份定稿能不能交程序」就是这么一条）：
- 决策记录：**只要定下了一件事就记**（选表 / 定字段 / 命名 / 改记录 / 放弃某个方案 / 更正之前的判断…，不只确认门那一次）。落点与格式见 `../sr-askme/references/decision-recording.md` —— 追加进**本功能**的 `decisions\决策记录.md`（一个功能只有一个决策文件）。
- **历史版本：不存** —— 审查报告属**过程档案**，按 `../sr-askme/references/version-history.md` §一「别的产物不在此列」**不要求留历史版本**；往已有报告追加新一节时**直接改同一份**，不要跑 `history_snapshot.py`（留痕只报数、不列条目，给它开版本会与这条口径打架）。
完成判据：审查基准已生效——每个数值知道该标什么，每章知道该长什么样。

### 第 2 步 · 盘点定稿与对照物

读定稿全文，盘点对照物：同主题成稿（**按文件名认**：`gdd\<主题>_成稿.md`；`<主题>_成稿_<日期>_<序号>.md` 那种是**留痕**，别当成成稿）、配置表、本功能的决策记录（`decisions\决策记录.md`）。只盘点，不评价。
完成判据：报告"输入"节所需信息齐全（定稿路径与 status、各对照物有/无）。

**成稿的定位判据是文件名，不是「没有 `_定稿` 后缀」**（2026-10-13 更正）：`gdd\` 下的 `<主题>_宣讲.md`、`<主题>_<日期>_审查.md` 同样不带 `_定稿` 后缀、也不是历史版本，按后缀反推会把它们认成成稿；成稿当前版的固定名只有 `<主题>_成稿.md`（见 `../sr-askme/references/version-history.md` §一）。目录里只剩改名前的带日期旧名（如 `联盟讨伐_20261009.md`）或压根没有时，按内容判断并向用户确认，不要静默按「无成稿」处理。

### 第 3 步 · 基础自检（V1–V9）

对照检查表逐项核对定稿本体，每项记录 通过 / 不通过 + 证据（章节、原文定位）。发现不通过时不改文，把证据写足——定位到"章节 + 条目 + 原文"级别，让 `/sr-gdd-fix` 能直接照单修复。
完成判据：V1–V9 每项有结论。

### 第 4 步 · 整合一致性（V10–V14）

V11、V13、V14 不依赖对照物，总要核；其余按对照物覆盖：

- 有成稿 → V12：按 `gdd-pipeline.md` 第二节章节对应表逐项核对，成稿设计结论无遗漏落进定稿，验证计划与已废弃口径正确地**未**进定稿；
- 有配置表 → V10 全查 + V5 抽查落地：标注 `表名.字段名` 的字段在表里真实存在、取值不冲突，§6 契约与实际字段一致；
- **V14 要真看图**：本 skill 里唯一需要打开图片证据的项——逐屏看画面本体（判"有没有"），再对标注 / 说明（判"全不全"），两源结果**分开记**，冲突处按 D21 的表列裁决；
- 缺对照物的项标"未核（缺对照物）"，不算不通过。
完成判据：V10–V14 每项有结论或明确标注未核原因；V14 已逐屏看过画面本体并把两源结果分开记录。

### 第 5 步 · 出报告并交给用户

按输出格式写报告落盘，向用户呈现结论与阻塞项，并说明三条去路：用户自行处理 / 转 `/sr-gdd-fix` 按问题清单修复（配置表问题转 `/sr-config`）/ 争议项当面裁决。本 skill **不改定稿**；但**审查结论本身是一条决策**（「这份定稿能不能交程序」就是这么一条），按上面的指针追加一条。
完成判据：报告已落盘到 `gdd\<主题>_<日期>_审查.md`（本功能目录下）；V1–V14 每项有结论或"未核 + 原因"；阻塞项已逐条点到"章节 + 条目 + 原文"；三条去路已向用户说明。

## 检查表

对每项输出：通过 | 不通过 + 证据（章节/原文定位）。标注（D<n>）的项，判据以 `../sr-askme/references/gdd-writing-discipline.md` 对应条目为准（含其「判据」列与成稿/定稿变体），本表只写查什么。

| ID | 项 | 查什么 |
|---|---|---|
| V1 | 状态与身份 | 顶部两字段合法且自洽：`doc_type: final_gdd`、文件名带 `_定稿` 后缀、`status` 在该 doc_type 的合法组内（`pending` / `active` / `provisional` / `blocked`；定稿的 `archived` **仅历史遗留文件**）；`provisional` / `blocked` 产物未被当作可交程序的正式定稿呈现 |
| V2 | 结构骨架 | 章节顺序与 `../sr-gdd-ai/resources/templates/feature-gdd.md` 骨架一致；**每节表头列名逐字一致；任何层级的标题都不得超出模板声明（含 `####` 及更深）**；子节只出现在模板声明的位置（`### R1 <规则组名>` / `### 5.1 UI-M1 <界面名>` / `### 6.N <工作簿文件名>.xlsx（<角色>）` 这类占位模式按实例数实例化，显得比模板"多"不算越界；**把元素拆成小标题写＝越界**）；**界面子节（§5.x）图数 1 张 + UE 表**（元素与状态的细节在既有 UE 行的规则格里，**正文不得重复 UE 表已写过的事实**）；不含成稿专属内容（验证计划章、已废弃口径章、附录 A 台账、证据编号、拍板记录等过程留痕）；**不含模板元说明** —— `feature-gdd.md` 里的**形状 / 组号 / 填写口径**说明块（**不论是否以 `>` 起头**，如 §4 的组号与「配置字段」列口径、§6 的「形状」、§7 的列口径）是给撰写者看的规范，**不得抄进定稿**；定稿该处只保留**范围声明 + 表格 + 表级核验注**（2026-10-15 实例：§7 的「列口径」曾被抄进两份定稿；2026-10-16 实例：§4 章首的组号与列口径说明块曾被抄进两份定稿，已清） |
| V3 | 规则写法（D1） | 逐条对照 D1 判据查规则章：规则可读性、组级编号、交叉引用 |
| V4 | 语言分层（D2） | 逐条对照 D2 判据查配置指代：规则正文、「配置字段」列与 §6 各归各位。**两处都要扫**：① §4 各规则的「细节」列；② **§5 全部界面的 UE 表**（UE 表列名只有「编号 \| 规则（详细）」，**没有配置字段列** ⇒ 字段名与系统级口径句在 §5 无处安放；D2 定稿变体：配置对应只写在 §4「配置字段」列与 §6）。只扫 §4 会漏（2026-10-13 实例） |
| V5 | 数值落地（D3） | 逐条对照 D3 判据（定稿侧变体）查每个数值的标注；有配置表时抽查标注的字段真实存在 |
| V6 | 当前口径（D4） | 逐条对照 D4 判据查历史性表述与新旧对照 |
| V7 | 界面章（D5/D6） | 逐条对照 D5、D6 判据查线框图、UE 表与归属边界声明 |
| V8 | 标注纪律（D8/D15） | 逐条对照 D8、D15 与 `evidence-boundary.md`「轻量标注」查标注：`【推断】`、`待确认：`、`[示例]`；**未定项是否都带 D15 的标签 + 三件套**（权威指针 / 当前值地位 / 影响边界），有无裸写的"待定 / TBD / 待补"；**`【待确认】` 是否落在入口 / 解锁 / 状态转换 / 消耗 / 奖励 / 结算 / 限制 / 公式 / 异常 / 版本范围上**（落在这些面上即不通过，须改成确定口径或 `【本版本不做】`） |
| V9 | 文本卫生（D9） | 逐条对照 D9 判据查术语一致性与过程叙事 |
| V10 | 配置契约 | §6 按工作簿分节（`### 6.N`）、每节给表清单/键表 + 字段表；**`状态` 记在表级**（表清单那一行）且取值合法（已有 / 新增 / 新增命名待定 / 待配表），**字段表与键表不带 `状态` 列**；**字段表 / 键表的「含义」列不得留空或写"待补字段说明"**（D18），每格能回答"该字段影响什么"；有配置表时与实际字段逐项核对一致 |
| V11 | 多语言文本 | §7 只列普通文本条目；**表头逐字等于 `../sr-gdd-ai/resources/templates/feature-gdd.md` §7 声明的列集** —— 基准八列 `键 / 中文文案 / 占位符 / 状态 / UI位置 / UI状态 / 触发 / 用途`，**键名未核验 / 未定的功能在第 2 位增列 `候选Key名` 成九列**（条件列）；`状态` 与 `UI状态` 取注册词表取值，不得自造；无 `n{gid}` / `d{gid}`（随配置表 gid 走）；`占位符` 统一 `$n＝含义（来源：…）`；文案与规则口径一致 |
| V12 | 上游完整性（有成稿时） | 按 `gdd-pipeline.md` 章节对应表：成稿设计结论逐项落进定稿无遗漏；验证计划、§12、成稿 §1 的「为什么要做」与 §2 玩家动词清单、附录 A 正确地未进定稿；成稿状态为 `archived` |
| V13 | 整合自洽 | §4 规则 ↔ §6 字段 ↔ §7 文案互相可追溯；范围门、埋点、验收标准与规则不矛盾 |
| V14 | 界面素材与对图（D19/D21/D22） | ① §5 每屏图注指向 `evidence\` 真源（不是 `gdd\` 下的副本）；② 素材含不含**标注带**已声明（不含 ⇒ 核对受限，须写明）；③ 逐屏做**两源分工**核对——判"画面上有没有"只看画面本体、判"状态全不全"只看标注 / 说明，**不得混用**（把标注里写的字当成画面上有、或拿画面缺席去删状态变体文案，都算不通过）；④ **状态 × 文案矩阵**是否覆盖该屏全部状态（典型：按钮文案随状态切换的位置）；⑤ "图上没有"的项是否按 **D22 分类**落标，有无含混的"待补 / 待确认"式写法；⑥ **责任划分**——**文案**（标题 / 按钮字 / 提示语 / 标签字）由文档负责、**直接写定义**，有无被误当"设计欠账"（给文案挂 `保留·待补图`、或把 tips / 标签字当漏画）；**交互表现**才挂 `待交互稿`，两者有无混淆 |

## 输出格式

````markdown
GDD 定稿审查：<主题>

## 结论
可交程序 | 建议修复后交付 | 需用户裁决

## 输入
- 定稿：<路径>（doc_type / status: …）
- 对照物：成稿（有/无）· 配置表（有/无）· 决策记录（有/无）

## 分层摘要
- 基础自检（V1–V9）：…
- 整合一致性（V10–V14）：…（缺哪项对照物写明）

## 问题列表
| ID | 位置 | 问题 | 建议 | 优先级 |
|---|---|---|---|---|
| V5 | §4 R2 | 概率只有裸数值，未标字段 | 补标 `表名.字段名` 或"待配表" | 阻塞 |

## 已通过项
- V2 …
````

结论判据：有阻塞级问题 → **建议修复后交付**；只有设计取舍、数值真源冲突等须用户拍板的问题 → **需用户裁决**；全过 → **可交程序**。`provisional` / `blocked` 定稿无论结论如何，报告开头保留前置分诊的注明。阻塞 / 非阻塞分档在问题列表优先级列体现。

## 产出规范

| 产出 | 路径（`<SR_WORKSPACE>\` 下） |
|------|------|
| 审查报告 | `<功能目录>\gdd\<主题>_<日期>_审查.md` |
