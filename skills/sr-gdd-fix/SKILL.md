# 功能 GDD 定稿修改工作流（SR-GDD-FIX）

## 功能说明

**唯一输出：改后的定稿**（改动清单随决策记录留档）。定稿通过后成稿归档、定稿成为唯一活文档，此后所有改动都由本 skill 落在定稿上（归属见 `../sr-askme/references/gdd-pipeline.md`）。**`pending`（定稿门之前）的定稿也可由本 skill 承接门内迭代**——此时不设 `approve`，是否过门由 `/sr-gdd-ai` 的定稿门决定。

- **不重跑整合**：只改用户指定的范围 + 影响面扫描（按纪律文件「影响面闭合」条目）扫出的受影响条目，不重新生成整份定稿、不回到 `sr-gdd-ai`。
- **不降低纪律**：修改与撰写吃同一套「撰写纪律」（`../sr-askme/references/gdd-writing-discipline.md`），大改动逐条自查。
- **配置侧不自己改表**：需要动配置表时调 `/sr-config`；改表后的定稿同步（§4 对应行、§6 契约）由它按自己的第 5 步完成。
- **文本不落表**：§7 只维护条目；文本表的增删改由用户自行发起。

形态基准：`../sr-gdd-ai/resources/templates/feature-gdd.md`（定稿骨架，本 skill 不重排结构）。**原地修改**当前定稿（`gdd\<主题>_定稿.md` —— 它**永远是同一个名字，不换版**），沿用其头部（`doc_type: final_gdd` + 原 `status`：`active` 保持 `active`，`pending` 保持 `pending`，不代用户过门）。每次**改写之前**先按 `../sr-askme/references/version-history.md` 存一版历史版本，见「产出规范」。

## 使用方法

```
/sr-gdd-fix <定稿路径> <要改什么>
```

或直接说人话，例如"把神话宝库定稿里每日次数从 3 次改成 5 次"、"给星海远征定稿补一个失败分支"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **定稿路径**：要改哪份定稿（`<功能目录>\gdd\<主题>_定稿.md`；只给主题时在**本功能目录的 `gdd\`** 下定位，多份候选项列给用户选，不默认取最新）。
2. **要改什么**：一句话说清改动意图（哪条规则 / 哪个界面 / 哪个字段 / 哪段文本）。
3. **状态**：目标文件头部必须是 `doc_type: final_gdd`，且 `status` 为 `active`（已生效定稿）或 `pending`（定稿门之前的门内迭代）；`provisional` / `blocked` 定稿先回 `/sr-gdd-ai` 补齐，未写头部字段的旧文档先让用户确认其是否为当前有效定稿。

用户补齐后再从第 0 步开始。

## 路径约定

`<SR_WORKSPACE>` / `<SR_PROJECT>` 取自 `%USERPROFILE%\.dsh\sr-workbench\config.local.json`；字段缺失、为空或路径失效时运行 `/sr-askme` 补齐；成组安装见 `../sr-askme/SKILL.md` §四。

## 执行流程

### 第 0 步 · 载入项目语境与撰写纪律

读 `../sr-askme/references/sr_project_context.md`（数值铁律与写作约束）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与改动归属）、`../sr-askme/references/gdd-writing-discipline.md`（撰写纪律，按其「适用」列取定稿侧条目）、`../sr-askme/references/evidence-boundary.md`（只用「轻量标注」一段）。
完成判据：语境已生效——改动涉及的数值按 `sr_project_context.md`「数值状态词」标 `表名.字段名` 或"待配表"，正文只留当前口径（核对点：第 5 步复核清单）。

### 第 1 步 · 读定稿、锁定改动

先读定稿头部 `doc_type` + `status`。若 `status` 为 `provisional` 或 `blocked`，停止并转回 `/sr-gdd-ai`；若缺少头部字段，停止并请用户确认它是否是当前有效定稿，确认后本次保存才补 `doc_type: final_gdd` + `status: active`。`active` 与 `pending` 都继续（`pending` 时额外提示：本次属门内迭代，改完仍要回定稿门）：读全文，把改动意图落到具体条目上（哪几条 R、哪个界面 / UE、哪个字段、哪段文案），并记下改动前的原口径（改动清单要用）。意图含糊时一次问清，不自行扩大范围。
完成判据：目标文档已确认是 `doc_type: final_gdd` 且 `status` 为 `active` 或 `pending`（或用户已确认无头部旧文档为当前定稿并将在本次保存补标），改动点逐条落到"章节 + 条目"级别，并已向用户复述确认。

### 第 2 步 · 影响面扫描

对每个改动点扫一遍受影响面（范围按纪律文件「影响面闭合」条目），产出**改动清单**（第 4 步照它改、第 5 步照它复核、第 6 步呈现并随决策记录留档——**不单独落 md**，改动要点写进决策记录那一条的正文）：

| 编号 | 改动点 | 涉及章节 | 连带影响 | 是否动配置表 | 处置 |
| --- | --- | --- | --- | --- | --- |

连带影响至少扫这些：规则 ↔ 界面 UE ↔ 范围门 ↔ 埋点 ↔ 验收标准 ↔ §6 字段对应 ↔ §7 多语言文本。扫到的项要么进清单，要么明确写"已核，不受影响"。

**这份清单同时定本次的复审档位**（口径唯一权威：`../sr-askme/references/gdd-pipeline.md` §四「改完的复审按改动清单分级」；这里只写怎么用）：上列七面**触及任一项 = 结构性** ⇒ 改完必调 `/sr-gdd-review` 全量复审；**一项未触及 = 轻量** ⇒ 不跑全量，走第 5 步自查 + 往同一份审查报告追加「改动后复核」。档位写进清单的"处置"列。**`pending` 的门内迭代不分级** —— 它沿用 `sr-gdd-ai` 第 5 步的"改完复审"（本次是不是 `pending`，第 1 步已确认）。
完成判据：每个改动点的连带影响都有结论；清单覆盖全部需要改的条目，无"待定"；**复审档位已定**并写进清单（结构性 / 轻量 / "本次是 `pending` 门内迭代、不分级"）。

### 第 3 步 · 配置侧（需要动表时）

改动需要新增 / 修改字段或数值时，**调 `/sr-config` 改表**——它按最小事务写入、读回验收，并顺手回写定稿 §4 对应行与 §6 契约。本 skill 不直接改工作簿。不涉及配置表时跳过本步并记"无需改表"。
完成判据：涉及配置表时 `/sr-config` 已 `PASS`（或明确列为阻断项并向用户报告）。

### 第 4 步 · 改定稿

按改动清单改定稿，执行撰写纪律的定稿侧适用项（条目内容与判据以 `../sr-askme/references/gdd-writing-discipline.md` 为准，此处不复制编号）：

- **最小编辑**：只动清单里的条目，不顺手重写、不重排章节、不改与本次无关的规则；
- **编号与术语**：沿用既有 R 组号、界面 ID（UI-Mx）、UE 编号（UEx）与术语；新增条目接在所属组末尾；
- **口径**：正文只留改后的当前口径（取代关系进改动清单，按纪律文件「当前口径」条目）；
- **数值**：落地值标 `表名.字段名`，未落表标"待配表"（按纪律文件「数值」条目定稿侧变体）。
- **逐屏对图核对（回写界面时必做）**：凡改动或新增 §5 的界面，逐屏对照素材做一次核对，产出**「状态 × 文案」矩阵**（哪个状态对应哪条文案），并按纪律文件「§5 对图核对」与「三类标注」两条收口。三个要点：

  1. **一屏只有一个状态** —— 图是样本、不是全集；**不得用"图上没有"去删状态变体文案**。
  2. **两源分工**：判"画面上有没有"只看**画面本体**（标注 / 说明文档里写着的字**不算画面上有**）；判"状态全不全"只看**标注带 / 界面说明**（画面缺席**不算**规则该删）。
  3. **冲突按表裁决**：

  | 画面本体 | 标注带 / 说明 | 裁决 |
  | --- | --- | --- |
  | 有 | 无 | 画面确实出现 → 标 `待设计确认`（疑漏标） |
  | 无 | 有 · **文案**（标题 / 按钮字 / 提示语 / 标签字） | **不适用待补标签** —— 文案的定义权在文档：直接在 §5 / §7 写定义即可。**UE 图只画状态样本、不穷尽状态与文案**，图上没有不代表文档缺（2026-10-16 用户口径） |
  | 无 | 有 · 状态变体 | 正常（图是样本）→ 把状态全体写进 §5 与 §7 的「触发」列 |
  | 无 | 有 · **交互稿**（行为与表现怎么画） | 才是设计欠账 → 标 `待交互稿`，进交接清单 |
  | 无 | 无 | 我们新加 → 标 `新增需求` |

  4. **真源只有一个**：核对以 `evidence\` 下的**导出真源 + 其说明文档**为准；`gdd\` 下的图片副本**不参与"图有没有"的判断**（副本只用于正文引用）。

完成判据：改动清单逐条落地；正文口径统一、无新旧对照；编号与术语无冲突；**改动涉及的界面已逐屏对图、状态矩阵已产出且无裸写**。

### 第 5 步 · 复核

通读改动范围与受影响章节。纪律类逐项（规则写法、配置指代、数值标注、口径、界面、标注、术语）按 `../sr-askme/references/gdd-writing-discipline.md` 定稿侧适用项核对；另核本 skill 特有项：

- [ ] 改动清单每条都已落地，无漏改、无超范围改动
- [ ] 影响面全部闭合（规则 / 界面 / 范围门 / 埋点 / 验收 / §6 / §7）
- [ ] 定稿结构未变（章节顺序与骨架与 `feature-gdd.md` 一致）
- [ ] 定稿顶部 `status` 保持原值（`active` 保持 `active`；`pending` 保持 `pending`，不代用户过门）；文件名保持 `<主题>_定稿.md`（**不换版** —— 定稿永远同一个名字）
- [ ] **改之前那一版已留成历史版本**（`<原名>_<YYYYMMDD>_<序号>.md`，落在同一个 `gdd\`；口径见 `../sr-askme/references/version-history.md`）
- [ ] **本屏对图核对已做**（改了 / 新增了 §5 的界面时）：状态 × 文案矩阵已产出，每个"图上没有"都按纪律文件的三类标注落了标签，**没有一件用"图上没有"当作删掉状态变体文案的理由**，也**没有把文案当成设计欠账**（文案直接写定义；只有交互表现才挂 `待交互稿`）
- [ ] **图注指向真源**：改动涉及的界面图注指到 `evidence\` 真源；没有拿 `gdd\` 下的副本当"图有没有"的判断依据
- [ ] **每节表头列名与 `../sr-gdd-ai/resources/templates/feature-gdd.md` 逐字一致；任何层级的标题都不得超出模板声明（含 `####` 及更深）；子节只出现在模板声明的位置**（`### R1 <规则组名>` / `### 5.1 UI-M1 <界面名>` / `### 6.N <工作簿文件名>.xlsx（<角色>）` 这类占位模式按实例数实例化，显得比模板"多"不算越界；**把元素拆成小标题写＝越界**，细节写进该子节正文的 `**元素名**：` 行内加粗、图注或既有表格子）——**界面子节图数 1 张 + UE 表，正文不重复 UE 表已写过的事实**

完成判据：清单全部通过；不过关则修订后复查。**复审按第 2 步定的档位收口**：

- **结构性** ⇒ 调 `/sr-gdd-review` 全量复审，拿到报告后再进第 6 步（报告与改动清单一并呈门）；
- **轻量** ⇒ 往**同一份**审查报告追加「改动后复核」一节（改动点 + 复核结论），不跑全量；**没有可追加的报告时降级为结构性**；
- **`pending` 门内迭代** ⇒ 回 `/sr-gdd-ai` 第 5 步收口，不走上面的分级。

一次改动只自动触发一次复审 —— 用户照报告裁决后再改的，**不再自动重审**（要再审由用户喊）。

### 第 6 步 · Human Gate

向用户呈现**改动清单（改前 → 改后）+ 改后的受影响章节**，等待选择：

```
active：approve / revise / reject
pending：revise / done（门内迭代不设 approve——是否过门由 `/sr-gdd-ai` 的定稿门批）
```
完成判据：用户已从上述选项中明确选择其一；**用户没表态之前不许替他写任何决策** —— 但用户每给一次拍板或纠偏，凡其中**含设计口径**的，按 `../sr-askme/references/decision-recording.md` 当场追加一条（门内迭代也各记一条；只含流程动作的不记，见下）。

本 skill 不设 `request_missing_evidence`——输入就是定稿本身，缺什么在第 1 步已问。

**门的结果本身不进决策记录**（`approve` / `revise` / `reject` 是流程动作，属 ADR 或不记）。要记的是**这次拍板里定下的设计口径**：用户在这一轮改了哪条规则 / 数值 / 命名 / 范围 / 界面或文案定义，就按 `../sr-askme/references/decision-recording.md` 追加一条 —— `**决策**：` 写设计口径本身（编号 · 改前 → 改后）；`**依据**` 写用户原话或证据；`**影响**` 写留历史版本时的新旧定稿路径与要同步的配置表。只改文档结构、格式、模板措辞、工具或落点的，记 ADR、不记这里。**选择发生在门内迭代里就当场记**，别攒到最后。

## 产出规范

| 产出 | 路径（`<SR_WORKSPACE>\` 下） |
|------|------|
| 改后的定稿（**原地更新**，维持唯一活文档） | `<功能目录>\gdd\<主题>_定稿.md` |
| **改之前那一版**（历史版本，每次改都留） | `<功能目录>\gdd\<主题>_定稿_<YYYYMMDD>_<序号>.md` |
| 改动清单 | **不单独落盘**——要点写进决策记录那一条的正文 |
| 「改动后复核」节（**仅轻量变动**） | 追加进本功能**已有的**那份审查报告 `<功能目录>\gdd\<主题>_<日期>_审查.md` —— 同一份，不新建、**不开历史版本**（审查报告属过程档案，见 `../sr-askme/references/version-history.md` §一） |
| 决策记录 | `<功能目录>\decisions\决策记录.md`（**追加**一条；格式见 `../sr-askme/references/decision-recording.md`） |

**改写定稿之前先存一版历史版本**（**每次改都存**，不是"用户要求才存"）：动笔前跑一次
`python "<sr-askme 技能目录>/tools/history_snapshot.py" "<定稿绝对路径>"` —— 它读目录实况算序号、
打印新版本路径。口径唯一权威：[`../sr-askme/references/version-history.md`](../sr-askme/references/version-history.md)。
新旧路径写进决策记录那一条的 `**影响**`。

★ **不再有「换版」**（2026-10-12 口径）：定稿**永远是同一个名字**（`gdd\<主题>_定稿.md`）——
不再"另存为新日期的定稿、新 `active` 旧 `archived`"。历代样子一律由**历史版本**承担；
`status` 只在 `pending → active` 这条线上走（旧的 `archived` 语义随之退休）。
