# 功能 GDD 整合定稿工作流（SR-GDD-AI）

## 功能说明

**输出：功能 GDD 定稿或工作版**。主线路径通过后才是 `active` 最终交付物；直接调用产出 `provisional` 工作版或 `blocked` 产物。按 `resources/templates/feature-gdd.md` 产出实现粒度的功能开发文档，交给程序实现：功能规则 Rn、界面流程、§6 配置契约、§7 多语言文本。**定稿只有 §1–§7 七章**（2026-10-30 口径）——范围门、数据埋点、验收标准、交接清单只留在成稿，不进定稿。

**详细度铁律**：定稿是**综合产物**——设计结果 + 配置落地 + 多语言文本；只写结果，不写整合过程。规则、界面、契约、验收写到程序可实现的粒度，不遗漏、不概括；数值以配置表实际落地为准标 `表名.字段名`，未落表的标"待配表"，不凭空写数。**宁可详尽标注待确认，不假装已定。**

**两条输入路径**：

- **主线路径**（首选）：输入 = `sr-gdd-human` 成稿（纯规则，设计已审核确认）+ `/sr-config` 的配置表（字段与记录已落）。本步把两侧**综合整合**——每条规则对应到配置表里实际落地的字段/记录，成稿 §11 的数值待定项落到实际配置，再据定稿生成多语言文案。
- **直接调用路径**：只有旧案/配置表、无需先出可读版时，从零执行本文件全部流程（含决议问答与全文撰写）。

**与成稿、配置表的分工、章节对应、两道门与退回方式：权威定义在 `../sr-askme/references/gdd-pipeline.md`**（第 0 步读入，本文件不复述）。一句话判据——成稿只有纯规则与设计（零配置指代）；配置字段由 `/sr-config` 从成稿规则派生；本步综合两侧整合成定稿并据定稿列出多语言文本条目。**整合只做一次**：主线路径定稿通过后成稿归档废弃，**定稿成为唯一的活文档**；直接调用只产出 `provisional` 工作版或 `blocked` 产物，不进入 `sr-gdd-fix`。主线路径的后续设计微调、字段对应调整、文本改动都交 `sr-gdd-fix`（或直接编辑定稿）。本 skill 只负责首次整合。

不提供一页设计 / 商业立项案等其它形态；商业 pitch 模板不适配内部功能开发文档。不编造缺失的上游材料——缺什么就列最小缺失清单，由人决定补不补。

frontmatter 写两字段（`doc_type` + `status`，定义见 `../sr-askme/references/gdd-pipeline.md` §一·补；**正文里没有任何头部说明块** —— 见 D19）：主线路径生成 `doc_type: final_gdd` 且 `status: pending`（整合完成、待第 5 步审查与定稿门），门 `approve / approve_with_conditions` 后改 `active`；发生设计问题、请求补证据或拒绝时改 `blocked`。直接调用路径生成 `status: provisional`，即使用户通过本次 Human Gate 也不升级为 `active`；缺少会改变决策的材料时改 `blocked`。**不换版、无 `archived`**（2026-10-12 取消换版）：定稿永远同一个名字 `AI读版策划案_<功能名>_正式版.md`，历代样子由历史版本承担（口径见 `../sr-askme/references/version-history.md`）。

## 使用方法

```
/sr-gdd-ai <主题或材料路径>
```

或直接说人话，例如"基于英雄改造v0.2.xlsx 出功能 GDD"、"把神话宝库的成稿和配置变更整合成定稿"。

## 无输入时的行为

裸调用纪律见 `../sr-askme/references/bare-invocation.md`。本 skill 收集：

1. **主题**：要首次定稿哪个功能的 GDD。**若该功能已有定稿**，说明这是修改任务，请用户改用 `/sr-gdd-fix`（本 skill 只做首次整合）。
2. **输入材料**（有就给路径，没有就明说没有）：
   - **sr-gdd-human 成稿**（`<功能目录>\gdd\`，首次定稿的主线首选输入）
   - 配置表 / 建表记录（`/sr-config` 产出或 .xlsx）
   - 旧策划案 / 脑图 / 提纲（直接调用路径的输入）
   - 体验记录 / 证据索引 / 竞品笔记（`<功能目录>\evidence\` 等）
   - UE/界面草稿、本功能的决策记录（`<功能目录>\decisions\决策记录.md`）

提示时同时告知材料要求：**首次定稿的最低输入是成稿 + 配置表**（配置没有就说明由谁补）；**直接调用路径**的最低输入是主题 + 能支撑规则粒度的描述（旧案、脑图、体验记录、配置表任一，或当场口述）。材料薄可以先生成 `provisional` 工作版；但缺少会改变规则、范围、投入或风险处置的材料时，必须标 `blocked` 并停下等补充，不把缺口用猜测填上。用户补齐后再从第 0 步开始。

## 路径约定

`<SR_WORKSPACE>` / `<SR_PROJECT>` 取自 `%USERPROFILE%\.dsh\sr-workbench\config.local.json`；字段缺失、为空或路径失效时运行 `/sr-askme` 补齐；成组安装见 `../sr-askme/SKILL.md` §四。

## 执行流程

### 第 0 步 · 载入项目语境与撰写纪律

读四份文件：`../sr-askme/references/sr_project_context.md`（数值铁律与写作约束）、`../sr-askme/references/gdd-pipeline.md`（三份产出契约与退回方式）、`../sr-askme/references/gdd-writing-discipline.md`（撰写纪律，本 skill 按其「适用」列取定稿侧条目自查）、`../sr-askme/references/evidence-boundary.md`（只用其中「轻量标注」一段）。
完成判据：语境已生效——定稿按 `sr_project_context.md`「数值状态词」处理每个数值：已落配置标 `表名.字段名`，未落表标"待配表"；§7 只收普通文本条目，正文不带过程留痕（核对点：第 3 步）。

### 第 1 步 · 资产盘点

列出用户提供的、以及**本功能目录**（`features\<主题>\`）下已有的输入材料：**sr-gdd-human 成稿**（主线首选，`gdd\`）、配置表变更/建表记录、概念与玩家承诺、体验记录、证据索引、旧策划案、配置表（.xlsx）、生产约束。只盘点，不评价。

输入含成稿时，同时核对成稿能否支撑定稿（下列为**成稿章号**）：§4 规则组、§5 界面清单、§11 数值待定项、附录 A（A.1–A.9，含 A.9 治理引用）。缺项在第 2 步分类处置。**成稿 §6 范围门、§7 数据埋点信号、§9 验收标准、§10 交接清单不进定稿**（2026-10-30 起），本步不核这四章、也不要为了它们补报材料；设计内容（规则组 / 界面）的缺口仍按第 2 步阻断。
完成判据：产出一份材料清单（名称 + 路径），每项标注"已有 / 缺失"。

### 第 2 步 · 缺失上游检查（VOI 门 + 决议问答）

对每个缺失项问一个问题：**它的可能结果会改变决策、范围、投入或风险处置吗？**

- 会 → 列为"最小缺失 artifact"，向用户报告后**停下等补充**（除非用户明确说继续）
- 不会 → 标注"可选学习项"，不阻塞

缺失不是自动补材料的理由；写到"足够做决策"就停。

**按路径分流缺项**：

- **主线路径（输入含成稿，且成稿仍是活文档）**：
  - 缺的是**留痕信息**（证据编号、假设来源、拍板记录）→ 一律标"可选学习项"，不阻塞。过程留痕不在定稿中重建。
  - 缺的是**设计内容**（规则组 / 界面有缺口，或规则自相矛盾、机制对应不到配置字段）→ 产物标 `blocked`，走「修订路由」：按 `gdd-pipeline.md` 第四节输出修订点清单、本次任务状态置 `BLOCKED`，退回 `sr-gdd-human` 定向修订。**本步不替用户拍设计取舍。**
- **改已有定稿**：若目标文档 `status: active` 或 `pending`，转告用户改用 `/sr-gdd-fix`（它按撰写纪律做影响面闭合与最小编辑；`pending` 即门内迭代，改完仍回本 skill 的定稿门）；若目标文档是 `provisional`、`blocked` 或无头部字段的旧文档，先按本流程补齐主线或材料，不把它当作 active 定稿修改。
- **直接调用路径（无成稿）**：材料只有提纲级描述（旧案 bullet、脑图）时，把会改变规则走向的关键取舍整理成**决议问题清单**（每条给候选 + 推荐 + 理由），请用户逐条拍板后再成稿。不替用户做设计取舍。直接调用产物保持 `provisional`；缺少会改变规则、范围、投入或风险处置的材料时，产物标 `blocked` 并停下等补充。

完成判据：每个缺失项都有 VOI 判定结论并归入上面某一条分支；主线路径的决议问答或直接调用路径的决议问答已逐条拍板；直接调用产物已明确标 `provisional` 或 `blocked`，不得宣称为主线 `active` 定稿。

### 第 3 步 · 撰写与整合

以 `resources/templates/feature-gdd.md` 为章节骨架依次撰写：**首次定稿**按 `gdd-pipeline.md` 第二节的章节对应表整合（该表第 0 步已读入，此处不复述），**直接调用路径**按同一骨架从零撰写。产出按 `../sr-askme/references/gdd-writing-discipline.md` 的定稿侧适用项自查（条目内容与判据以该文件为准，此处不复制编号）。

整合时只需盯住三件事：

1. **规则与字段的对应**：§4 每条规则对应到配置表里实际落地的字段/记录，规则组号沿用成稿（拆出的新主题另起组号）；对应不上的在 §6 **表清单的「状态」列**标 `待配表`（表还没建也照列），不自行发明配置项。**组号与「配置字段」列口径是撰写侧约定，不写进定稿**——定稿 §4 不留章首说明块（见模板 §4 的元说明）。
2. **§6 配置契约从配置表读回**：每张工作簿一节（`### 6.N`）→ 该工作簿的**表清单**（中文表名 / 输出名与映射名 / 索引 / **状态**：已有、新增、新增命名待定）→ 每张表的**字段表**（中文字段 / 英文字段 / 结构 / 含义）；既有 key-value 表给**键表**；依赖的外部表单列一节。**状态记在表级，字段表与键表都不带状态列**（形状见 `resources/templates/feature-gdd.md` §6）。
3. **§7 多语言文本只列普通文本条目**，按模板**八列写全**（键 / 中文文案 / 占位符 / 状态 / UI位置 / UI状态 / 触发 / 用途，列名与列序逐字照模板 §7；**键名未核验或未定的功能按模板增列 `候选Key名`**），本步到此为止——**文本表的增删改由用户自行发起**，本 skill 不调用落表工具。八列直接对齐下游「正式 AI读版 · 多语言引用」的列，做到转置零推断（`UI状态` 用工程枚举；`占位符` 统一 `$0`/`$1` 并写清含义、来源与是否可选；`状态` 取模板的**注册词表**、不得自造）。表下必写**表级核验注**（文本源文件 + 条目数 + SHA256 + 核验结论）——**没有核验证据不得写 `已核验Key`**；`键` 列只放已核验官方键名或 `待分配Key`，建议名进 `候选Key名` 列。GID 名称/描述键 `n{gid}`/`d{gid}` 不在此列（两类多语言的区分见 `../sr-askme/references/sr_project_context.md`）。

**详细度要求（本步核心）**：

- **不遗漏**：成稿/旧案的全部**设计结论**（规则、界面）映射进定稿对应章节，成稿后逐项核对；**范围门、埋点、验收标准、交接清单只留在成稿，不进定稿**——不要为了"完整"把这四章搬进定稿；
- **界面章节**：为**每个关键界面**单独给出 ASCII 线框图（布局 + 控件 + UE 交互标注）+ UE 规则表（逐条编号 UE1…）+ 界面清单总览 + 流程 text 图 + 状态机（如适用）+ 全局交互规范；层级总图代替不了单界面图；嵌套的解锁/失败分支/默认回退用层级缩进列表；**有截图的界面把图放 `<功能目录>\gdd\assets\images\`，正文按 D19 用相对路径 `assets/images/<文件名>` 内联**；
- **规则粒度**：每条 R 规则条件/动作/结果/边界齐全，程序可直接实现；
- **执行语义完备**（D13/D14）：除粒度外跑两遍扫描——① **特殊态 × 规则组**：血量/数量按无限处理、数值为 0、空槽、达上限、唯一实例或互斥、跨周期与结算期、并发与离线、退盟或解散导致的归属变化——每个特殊态与**每条相关规则**的交叉都要有成文结论（缺一格就是下游的阻塞性追问）；② **成对闭合**：消耗 / 获得 / 结算的数量口径 + 扣发时点 + 失败回滚必须成对，公式、概率、阈值、例外给可执行口径，不写"按常规""沿用既有"；
- **开放项带处理状态**（D15）：未定项一律用标签 + **三件套**（权威指针 `表名.字段名` / 服务端字段 + 当前值地位 + 影响边界），不得裸写"待定""待补"；**`【待确认】` 不得落在入口 / 解锁 / 状态转换 / 消耗 / 奖励 / 结算 / 限制 / 公式 / 异常 / 版本范围上**——这些面要么定，要么标 `【本版本不做】`；
- **§5 ↔ §7 双向对扫**（D16）：§5 每个界面里出现的玩家可见文案，§7 必须有键或在该处显式写"此处不需要文案"；反扫 §7 每个键在 §5 有落点；界面状态按类别逐类覆盖（可用/不可用、确认/取消、成功/失败、空/等待/冷却、奖励/消耗/结算），不适用也留一条结论；
- **§6 字段用途与配置角色**（D18）：字段表 / 键表的「含义」列写清该字段**如何影响规则 / 状态 / 公式 / 显示 / 限制**，不得留空或写"待补字段说明"；配置角色标到 `文件.xlsx:Sheet!Range` 粒度（策划语义来源 / 配置事实来源 / 不纳入），外部表写清"引用它的什么、用在哪条规则上"；
- **权威边界与图片角色**（D19）：**定稿正文不带头部说明块**（2026-10-28 用户口径：「用途 / 结构 / 图片」三行对下游制作无用，已从模板与正文中删除 —— frontmatter 之后直接是 H1 与 §1）；**正文内联的图片统一放 `<功能目录>\gdd\assets\images\`（`gdd\` 下唯一的图片位，不再按批次另建 `界面素材_*` 目录、也不再直接引用 `..\evidence\…`）**，正文用**相对路径** `assets/images/<文件名>` 引用 —— 定稿就躺在 `gdd\` 里，整包搬走也不断图；图片给清单，图注写 `界面ID + 状态` 与角色（正式界面证据 / 仅视觉参考 / 配置为权威）；对图核对以 `evidence\` 真源为准（这是撰写纪律，不写进正文）；
- **正文行内标注**（按 `evidence-boundary.md` 的「轻量标注」）：推断内容标 `【推断】`；未定项写 `待确认：<事项>`；示例值标 `[示例]`，示例值不冒充配置值；**配置值不标 `[真实]`**——数值以配置表为准、随时会改，正文只写 `表名.字段名` 指向它。来源标签、Evidence Ledger、假设/风险台账属于过程留痕，只留在成稿。

输入含配置表（.xlsx）时，表内数值视作**修改或新增配置的来源**，可直接引用：标注 `表名.字段名` 并注明出自该 xlsx（状态为"待录入 `LuaConfigs` / `RPG_Configs`"）。xlsx 未覆盖的数值按数值铁律标"待配表"。
完成判据：模板每一节都有实质内容，或按 D15 的标签 + 三件套显式标注（不得裸写"待定"；执行语义面上不得出现 `【待确认】`）；**定稿章节只到 §7**（§8 范围门 / §9 埋点 / §10 验收标准 / §11 交接清单不得出现）；**设计结论无遗漏，且正文无过程性内容与模板元说明**（无证据编号、无假设台账、无拍板记录，也不抄模板的形状 / 组号 / 列口径说明块）；**frontmatter 之后除 `# 功能 GDD：<功能名>` 外没有任何 `>` 头部说明块**（用途 / 结构 / 图片那三行已退休）；状态按输入路径已标为 `draft`、`provisional` 或 `blocked`，未把直接调用产物标成 `active`。

### 第 4 步 · 治理复核

过程留痕由成稿附录 A 承载。本步只复核成稿 A.9 治理引用五条齐全、无占位符；定稿不设治理引用节、也不带来材料清单，不在交付物中重复填写。
完成判据：主线路径下 A.9 五条齐全；直接调用路径无成稿时，按 `../sr-askme/references/governance-check.md` 复核五条，**结论随第 6 步的决策记录留档（写进那一条的正文），不写入定稿**。

### 第 5 步 · 定稿审查（仅主线路径，必经）

调 `/sr-gdd-review` 对刚生成的定稿（`doc_type: final_gdd` + `status: pending`）做只读审查，拿到审查报告后再进定稿门。审查发现的问题在本步处理：能改的直接改，也可交给 `/sr-gdd-fix`（`pending` 模式）承接，改完复审——**`pending` 期间的改稿都不构成过门，定稿门仍由本 skill 收口**；属于设计问题的走第 2 步修订路由；须用户拍板的列为门上的争议项。直接调用路径跳过本步——`provisional` / `blocked` 产物不交程序，不做审查。
完成判据：主线路径已产出审查报告并逐条处置（已修 / 已退回 / 已列为争议项），报告结论随定稿一并呈给用户；直接调用路径已明确跳过并说明原因。

### 第 6 步 · Human Gate

向用户呈现定稿**与审查报告**，**突出整合结果**（规则与配置字段的对应、§6 配置契约、§7 多语言文本），等待选择：

```
approve / approve_with_conditions / request_missing_evidence / revise / reject
```

**呈门时同样要把「线框图」那一项提到**（`../sr-askme/references/使用说明.md` 主线第 3 步）：定稿已经产出，若 §5 仍是 ASCII 线框图，用户可以选择现在换成真线框图 —— 改动走 `/sr-gdd-fix`（替换 UI 可能带来功能改动，按其影响面闭合规则扫界面 ↔ 规则 ↔ 验收），不在本 skill 内改。不要因为"定稿门只批整合结果"就不提这一步。

定稿与审查报告呈现后用户提出修订或拍板时（revise 循环及任何门内迭代）：每轮先按 `../sr-askme/references/calibration-recording.md` 实时追加一条校准记录，再改定稿、再呈门。

完成判据：用户已从上述选项中明确选择其一，且已就整合结果表态；**用户没表态之前不许替他写任何决策** —— 但用户每给一次拍板或纠偏，就按 `../sr-askme/references/decision-recording.md` 当场追加一条（门内迭代也各记一条）。主线路径通过（`approve / approve_with_conditions`）后定稿状态改为 `active`、成稿归档；直接调用通过后定稿仍为 `provisional`，不进入 `sr-gdd-fix`。

用户选择后按 `../sr-askme/references/decision-recording.md` **追加一条决策记录**：`**决策**：` 写这次拍板（approve / approve_with_conditions / request_missing_evidence / revise / reject）与定稿结论，条件写在同一句里；`**影响**` 写定稿状态（`active` / `provisional` / `blocked`）、成稿归档与要同步的配置表。
