# 0013 · 手工删掉功能之后，面板收拾自己留下的痕迹

> 触发：2026-10-13 用户实测 ——「我手动删了功能，这个没有清理吗。需要优化一下」。
> 他是在资源管理器里把 `features\<主题>\` 删掉的（那是**正常**的撤法：面板没有删除入口），
> 结果工作区登记、工作会话、面板本地那条映射**一个都没跟着走**；他只能自己去侧边栏逐条清。

## 背景

「新建功能」建的不只是一个目录 —— 面板一共留下**四样**东西（见 `src/client.js` 的 `createFeature`）：

1. `features\<主题>\` 与 4 个桶（**文件**，用户删得掉，这是撤功能的正经动作）；
2. 一条**专属工作区**登记（侧边栏一行，指向那个目录）；
3. 一条**工作会话**（标题 `策划工作台·工作（<主题>）`，cwd = 功能根）；
4. 本地映射 `localStorage['sr-wb.work.v1']`：功能根 → 工作会话 id。

用户删掉 ① 之后，②③④ 全部留着：侧边栏一条点开即空的工作区、一条再也用不上的会话，
面板自己也还记着它。实测现场（2026-10-13）：`.dsh\sessions\` 下仍有 `~795E~8BDD~5B9D~5E93`
（神话宝库）等 4 个已删功能的目录 —— 这些**只有用户手工清**才会消失。

纪律上的张力：v5 明文「面板只建不删」（`CONTEXT.md` §面板与 skill 的分工、`client.js` 文件头）。
但 ②③④ **不是用户的数据**，是面板自己造的登记 / 会话 / 缓存 —— 收拾自己的东西不是"删用户的东西"。

## 决定

1. **清理的是"面板自己留下的痕迹"，不是用户的文件**。三条动作，**一条都不碰文件**：
   - `workspace.archiveSession({ sessionId })` —— 侧边栏**归档**（可取消归档，不是删除）；
   - `workspace.delete({ workspaceId })` —— 移除工作区**登记**（宿主口径原文：
     "Delete one Workspace registration **without deleting its directory or Sessions**"）；
   - `workCachePrune` —— 清本地那条映射（以及内存里同名的那张表）。
2. **判据只认面板自己造的**（`src/pure/leftovers.ts`，一处不抄两份）：
   工作会话必须标题是 `策划工作台·工作（…）` **且** cwd 落在 `<SR 工作区>\features\` 下；
   工作区必须**路径**落在同一个 `features\` 下。别人的会话 / 别处的工作区一律不判。

2.5 **已归档的会话不再判** —— 这一条是上线当天被用户逼出来的（原话「这什么玩意 怎么一直在」）：
   归档**不会**让会话从 `remote.session.list` 里消失（`SessionListRequest` 只有可选 cursor，
   列表不按归档过滤，只是官方侧边栏把它藏起来）。判据若不排除归档集，就会
   「归档 6 条 → 它们仍在列表里 → 下次重挂载/刷新又判成残留 → **再归档一遍、再报一遍**」。
   归档集**拿不到时一个都不判** —— 宁可不干活，也不要反复再归档（与 `sessionpick.ts` 同一条纪律：
   `[]` = 明确知道一条都没归档；拿不到 = 如实降级，别装成空表）。
   回执里会话名**去重显示**：历史残留常有同名会话（实测「联盟悬赏」一次占了 6 条里的 3 条，
   那是功能改名前的几代工作会话），条数照实报、名单只列一次。
3. **判据是磁盘事实，不是看板快照**：「残留 = 这些痕迹指向的功能目录**已经不在了**」——
   由组合根 `listDir` 逐个探测（只读），探测前先拿 `features\` 根做**通道自检**：
   连它都列不出来就返回"探测不可用"，调用方**一个都不判**。
   ★ 为什么不能用看板（扫 `features\` 得到的那份列表）当判据 —— 这是当天第三次被用户实测打回来。
   看板与侧边栏 store 是**两个数据源，更新时序不一样**：新建功能时 `syncSidebarStores` 会
   **当场**把新工作区并进 store，而看板要等 `refresh()` 之后的下一次请求才含它 ——
   中间那个窗口里「新工作区 + 旧看板」和「孤儿工作区」在数据上完全一样，
   于是面板把自己**刚建出来的**工作区登记删掉、刚建的会话归档掉
   （用户实测：「又新建了一个 测试用例，这次只创建出文件夹，工作区没创建」）。
   补一句"等看板刷新到最新一轮"的守卫（`dashRevRef`）**也不够** —— 触发清理的那次重渲染
   来自 store 更新，那时 `rev` 还没动，守卫根本看不到差别。
   换成磁盘事实之后这个窗口**天然不存在**：目录就在那儿，谁都判不出残留。
   ★ **"一个功能都没有"照样判**（用户指出「看板怎么可能是空呢 不是有新建功能入口吗」）：
   空数组是一份可信的"全集"，这时 `features\` 下的工作区与会话本来就全是残留。
4. **自动做，且如实报一句**：这是收尾，不该再要用户点一次确认。真清到东西才说一句
   （说清清了哪个功能、做了什么、怎么撤回）；**没残留就一个字节都不出现** —— 用户口径明确：
   界面不放"整理建议"类常驻提示（"侧边栏里有 N 条索引会话"那种已经被要求删过一次）。
   失败也如实说（不许假装清干净了）。

## Considered Options

- **什么都不做，让用户自己去侧边栏清**：否 —— 那正是用户来报的那件事（他刚手工清过一轮）。
- **给面板加"删除功能"入口**（连目录一起删）：否（这一轮）—— 删目录 = 删用户数据，纪律与风险都不是一次能拍板的；
  手工删目录**继续是**撤功能的正经动作，本 ADR 只是让删完之后不再留尾巴。
- **清之前先弹一次确认**：否 —— 动作可逆（归档可取消）、不碰文件，且判据有安全阀；多一次点击换不来等量的安全。
- **常驻一行"有 N 项残留〔清理〕"**：否 —— 违背"界面不放整理建议"的既有口径（见上）。

## Consequences

- **上线当天被用户实测逼出三处修正**（都已落进上面的决定，值得单独记一笔）：
  ① **归档集必须排除** —— 否则「归档 → 它仍在列表里 → 再归档 → 再报」，用户原话「这什么玩意 怎么一直在」；
  ② **"看板为空"不是刹车信号**（用户反问「看板怎么可能是空呢 不是有新建功能入口吗」）——
     安全阀要卡在"数据可不可信"上，不是"数据看起来正不正常"上；
  ③ **判据从"看板快照"换成"磁盘事实"** —— 这条最凶，也最能说明问题：先加的"等看板刷新到最新一轮"
     （`dashRevRef`）守卫**没能拦住**，因为触发清理的那次重渲染来自侧边栏 store 更新、`rev` 还没动。
     用户第二次实测「又新建了一个 测试用例，这次只创建出文件夹，工作区没创建」时的现场是：
     `workspace.json` 的最后写入时间与他那条新会话的创建时间**是同一秒** —— 建了，又被自己删掉。
     换成"目录确实不在磁盘上"之后，这个窗口天然不存在。
- ★ **同一个根因在这一轮发作了两次**：第一次是视图校验拿旧看板误报"没找到"（8.1.7 修），
  第二次是本 ADR 的清理逻辑。教训：**"拿快照当判据"这件事，在被用来做破坏性动作时严重得多** ——
  只读逻辑拿旧快照最坏是显示不对，破坏性逻辑拿旧快照最坏是删掉刚建好的东西。
- `CONTEXT.md` §面板与 skill 的分工补上这个唯一例外；`client.js` 文件头同步。
- **提示的分寸**（同一天用户第三次反馈后定下来的口径）：「建好了」那一句只说结果 ——
  `建好了：「X」· 4 个桶都在 · 专属工作区与工作会话已就绪。`
  原先它拖着绝对路径 + "要撤掉就删掉这个目录（面板不碰文件、会话会被归档…）"，提示下面还挂着
  "目录是索引会话跑的 PowerShell""本机只有 native""默认已是完全权限，不用再切"那几条 ——
  用户原话：「**这些不是用户需要看的，删掉后面这些**」。
  做法：`createFeature` / `createSessionAt` / `ensureWorkSession` 一律返回**两个**数组 ——
  `note`（诊断：常态实现细节，界面不显示，测试与排查仍读得到）与 `warn`（**有后果的降级**：
  工作区没登记上、预设没挂上、权限没切上、侧边栏没同步上、会话列表读不到）。
  界面**只显示 `warn`**，没有降级就一个字都不出现。撤销办法留在本 ADR 与操作文档里，不占每次新建后的提示。
- 新增判据用例 `test/pure-leftovers.test.ts`（安全阀：列举失败或被截断 / 锚点不在 / 没拿到列表 / **拿不到归档集**，
  以及"看板一个功能都没有照样判"与"已归档的会话不再判"），
  以及端到端用例 `test/panel-view-timing.test.ts` 的两条：真有残留 ⇒ 归档 + 移除登记且**不碰文件**；
  没残留 ⇒ 一个字节都不出现、也不白发动作。
- **判据跟着数据漂移的旧账一并清了**：`test/pure-topic.test.ts` 原来钉三个**具体主题名**
  （联盟讨伐 / 神话宝库 / 诸神降临）—— 用户删掉功能后它就红了，而红的原因不是代码坏了。
  改成跟着 `features\` 目录走的性质断言（有产物就得对得上名字，空目录跳过）。
- 遗留（未做，等真要时再立票）：
  · 面板**不删目录**，撤功能仍需手工删（或将来加删除入口，那要另立 ADR）；
  · **孤儿会话日志文件**（`.dsh\sessions\` 下的 `session.v4.jsonl.zstd`）由 DSH 管，面板不碰 ——
    归档只让它在侧边栏消失，磁盘占用不释放；
  · 列举**被截断**时不清理（那一轮的功能列表可能不全）—— 为此 `loadDashboard` 现在会为
    `truncated` 单独给一句 `note`（**原来这个字段根本没人看**：`listDirs` 把它吃掉了，
    于是"列举被截断"和"功能都被删了"在数据上完全一样）。这是本 ADR 顺带堵上的一处真缺口。
