# 0015 · 一次派活一条会话（四入口每次新建 + 两条护栏）

> 触发：2026-10-13 用户指令 ——「确实我想要的是：**每点一次四入口就另起一条全新会话**，新建会话也是新建一条会话。
> 虽然不能共享会话上下文，但是会减少压缩吧。这么做有什么坏处吗」。
> 我先把六条代价摆出来（并行写同一目录 / 新会话不知道之前定过什么 / token 账不是单向省 / 侧边栏堆同名会话 /
> 看进度的入口 / "接着聊"变成一次性），用户拍板：**核心改 + 两条护栏 + 发完切过去**。

## 背景

v5 起四入口的行为是"**认领复用**"：`ensureWorkSession` 按「内存 → 本地缓存 → 标题 `策划工作台·工作（X）` + cwd 恰好是功能根」
找一条已有的工作会话，找不着才建；`sendToWorkSession` 把指令用 `mode: "queue"` 发进那一条。

- **好处**：同一功能的四入口共享上下文，指令串行排队，不会两个 agent 同时写同一个功能目录。
- **代价**（用户要换掉它的理由）：那条会话越跑越长 —— 上下文压缩、注意力被前几轮稀释；
  一个功能的活其实是**几次独立的派活**，硬塞进一条对话里并不自然。

改成"一次派活一条"之后，新会话**没有上一轮的对话记忆**。四入口的指令本身是自包含的
（素材 / 落点 / 文件名 / 格式都在正文里，`pure/intake.ts`），但 persona 的决策记录契约只要求
"往 `decisions\决策记录.md` **追加**"、**没要求开工先读它** ⇒ 不补一道，新会话会重复问已经答过的问题、
或者给出与既有决策相冲突的结论。

## 决定

1. **四入口每次派活都新建一条会话**：`sendToWorkSession` → `newWorkSession`（与详情页〔新建会话〕
   **同一条创建路**：功能工作区 + 预设「策划模式」+ 改名 + 完全权限 + 并入侧边栏 store）。
   旧行为里那条"认领复用"的路**删掉**（`ensureWorkSession` 从组合根移除；`pure/sessionpick.ts` 的
   `pickWorkSession` / `needsFullAccess` 留在原处，暂时没有生产调用方 —— 见 Consequences 的遗留）。
2. **护栏① · 并行确认** —— **做过，当天就撤了**（记在这里，免得以后再想加回去）。
   撤的理由是用户一句话：「护栏1好像没啥用，**我同时跑两个头脑风暴不行吗**」。判据错在**触发条件**：
   它拦的时机是"这个功能还有会话在跑"，而那**恰好就是并行派活的常态** —— 等于每次正常用法都要多点一次。
   并发的真风险（两条会话同时写同一个功能目录）改由**写入规则**治：
   `decision-recording.md` §二 ＋ persona 都写明"**只追加、不许整篇重写**、报占用就重试"——
   丢一条决策是"事后看不出来"的损坏（时间线照样连续），所以判据要落在写的那一下，不该落在"让用户多点一下"。
   口径：**面板不替用户判断该不该并行** —— 他点几次就发几次。
3. **护栏② · 先读盘**：指令正文加一段（四入口**共用一处**，`intake.ts` 的 `pack()`，插在第一行之后）：
   你是这次派活新开的一条会话、动手前先读 `decisions\决策记录.md` 与 `analysis\` 既有产出。
   上下文断层的代价全部落在这里 —— 连续性从此靠**盘上的决策记录**，不靠对话记忆。
4. **发完切到那条新会话**（`uiWorkspace.openSession`）：用户点这一下就是要看活怎么干。
   **有降级就留在面板**把话说清（工作区没登记上 / 预设没挂上 / 权限没切上 / 侧边栏没同步上）——
   切走 = 面板重挂载、`notice` 是组件 state，那句话会跟着没（与 ADR 0014 同一条分寸）。

## Considered Options

- **维持"认领复用"（同一条会话串行排队）**：否 —— 用户明确要"一次一条"，长会话的压缩与注意力稀释是他要避开的损耗。
- **每次新建但不做并行确认**：否 —— `decisions\决策记录.md` 是"读全文 → 追加 → 写回"，
  两条会话并行写就是**后写的覆盖先写的**；丢一条决策属于事后极难发现的损坏，值得多一次点击。
- **在面板上做"并行确认"**（有会话在跑就先提示、再点一次才发）：**做过，当天撤掉** —— 见决定 2。
  它拦的是**正常用法**（并行派活就是这个口径的目的），而它想防的那个风险治错了地方。
- **硬拦（有会话在跑就不许发）**：否 —— 同上，而且更糟：用户正是要并行。
- **给会话标题加序号**（`策划工作台·工作（联盟讨伐 ·2）`）区分多条：这一轮**不做**。
  标题同时是**清理判据**（`pure/leftovers.ts` 的 `workTopicOfTitle` 从标题反推主题，再判"功能目录还在不在"）：
  序号加在括号**外** ⇒ 反推不出主题、这些会话永远清不掉；加在括号**内** ⇒ 会被当成"联盟讨伐 2"
  这个不存在的功能而**误归档**。要加就得把反推主题改成按 cwd 来，另立一票。
- **顺手删掉 `pickWorkSession` / `needsFullAccess`**：否（这一轮）—— `pure/sessionpick.ts` 正被另一票改动，
  且它们仍是被文档与用例引用的认领判据；删它们要连用例一起删，留给下一次清理。

## Consequences

- **同一功能下会有很多同名会话**（`策划工作台·工作（<主题>）`），面板不删不归档 ⇒ 它们不会自动收敛
  （只有功能目录被手工删掉时，残留清理才会把它们归档，见 ADR 0013）。侧边栏会越来越长，
  这是这个口径**明码标价的代价**；要收拢得另立一票（"归档更早的工作会话"）。
- **面板的工作会话指针改了含义**：`WORK_SESSION` + `localStorage['sr-wb.work.v1']` 不再是"指令的收件人"，
  只剩 ① 界面如实说"这个功能派过活 / 最近一条是哪条"、② 功能被删时连同它一起清掉。
- `ensureWorkSession` 删除后，`pure/sessionpick.ts` 的 `pickWorkSession` / `needsFullAccess` 在生产侧
  **没有调用方**（纯函数与用例仍在，判据没放宽）—— 下次清理票里一并处理。
- **并行写同一个功能目录**从此由**写入规则**兜底（`decision-recording.md` §二 + persona：只追加、
  不整篇重写、报占用就重试）—— 面板**不做**任何并发闸门，用户点几次就发几次。
  残留风险如实记：**同一个入口同一天连发两次**，产出文件名一样（`analysis\` 的文件名带日期）⇒ 后者覆盖前者；
  那是产出命名规则的事，面板拦不了。
- 判据：
  · `test/create-flow.test.ts`：每次派活都新建（正文逐字、预设、queue）；**连发两次 = 两条会话**；
    **撤护栏的钉子**（组合根上不再有 `__runningWorkSessions`，有会话在跑也照发）。
  · `test/panel-view-timing.test.ts`：派活 ⇒ 另起一条并**当场切过去**；有会话在跑时**一次点击就发**
    （不再有"再点一次"那句）；〔新建会话〕那条断言"四入口不复用它"。
  · `test/pure-brainstorm.test.ts`：四入口正文**都**带"你是新开的一条会话 + 先读决策记录与既有产出"那段，
    且插在第一行之后（两处路径写全）。
- 未做（等真要时再立票）：标题序号与按 cwd 反推主题；多条会话的收拢/归档；`pickWorkSession` 死代码清理。
