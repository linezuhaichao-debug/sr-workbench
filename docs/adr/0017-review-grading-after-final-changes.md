# 0017 · 定稿改动后的复审**分级**（成稿不审）

> 触发：2026-10-13 用户提——「我想策划模式里每次生成定稿、成稿后都调用 sr-gdd-review。每次修改定稿默认使用 sr-gdd-fix，然后调用 sr-gdd-review。你先考虑一下这样做好不好」。
> 评估后用户拍板：**成稿不调**（`sr-gdd-review`）；**定稿做，按分级**。

## 背景

**当时的调用面**（穷尽扫过一遍）：`sr-gdd-review` 只有**一个**自动触发点 —— `sr-gdd-ai` 第 5 步（首次整合、定稿门之前，仅主线路径）。其余是用户显式调用，或 `sr-gdd-fix` / `sr-gdd-ue` / `sr-gdd-html` 写一句"建议先走"。面板、常驻 persona、`sr-gdd-human` 三处**都不提它**。

- **缺口是真的**：定稿门通过后成稿归档，**定稿成为唯一活文档**——而改动它的收口只有 `sr-gdd-fix` 自己第 5 步那份自查清单。改坏了没有第二道网。
- **但"每次改动都全量审"不成比例**：review 是"这稿能不能交程序"级的核对（V5 逐字段比配置表、V11 跟 `normaltxt.xml` 9,068 键逐名比对）。实测体量：联盟讨伐那次 21 项 / 报告 39KB；圣物系统那次 3 项 / 10KB。
- **成稿侧接不住**：review 的 13 项检查表是按**定稿形态**写的，两边章节编号还错位（成稿 §6 是**范围门**、§7 是**埋点**；定稿 §6 是**配置契约**、§7 是**多语言文本**）。逐项对下来——
  - 可直接复用 **4 项**（V3 规则写法 / V9 文本卫生 / V1 改字段值 / V5 换成稿变体）；
  - 要**反着写** 3 项（V2：定稿要求"**不含**验证计划章 / §12 / 附录 A"，成稿是"**必须含**"）；
  - **V10–V13 完全不适用**（成稿没有 §6 契约、没有 §7 文本、零配置指代；V12 的方向还是反的——成稿是上游）。
  - 而成稿**真正独有**的四项（D7 上游映射、D10 附录 A 台账、§11 待定项收全、结果章无留痕散落），review 一项都没有。
  ⇒ 挂 review 上去等于**再写半套检查表**，还会让"能不能交程序"这个目的漂掉（审一份还不含配置的中间产物，只会得到一片"未核（缺对照物）"）。

## 决定

1. **成稿不设审查**：`draft_gdd` 不进本流程，批它的是成稿门（批"设计与留痕"）。落点 `gdd-pipeline.md` §三 + `sr-gdd-review/SKILL.md` 分诊表；review **保留**"用户坚持时才审"的例外，但要求报告里把 V10–V13 逐项标"不适用"。
2. **定稿改动后的复审按改动清单分级**（权威写在 `gdd-pipeline.md` §四 新增小节，其余文件只留指针）：
   - **结构性改动** —— 触及纪律文件「影响面闭合」条目所列任一面（规则 / 界面 UE / 范围门 / 埋点 / 验收标准 / §6 字段对应 / §7 多语言文本）⇒ **改完必调 `/sr-gdd-review` 全量复审**，报告与改动清单一并呈 `sr-gdd-fix` 的门。
   - **轻量改动** —— 七面**一项都没被触及**（只动数值落地标注或文案措辞）⇒ **不跑全量**：走 `sr-gdd-fix` 第 5 步自查，并往**同一份**审查报告追加一节「改动后复核」（改动点 + 复核结论）。**没有可追加的报告时降级为结构性**——顺手把报告建起来。
   - **只管定稿门通过之后这一档**：`pending` 的门内迭代**不分级**，它沿用 `sr-gdd-ai` 第 5 步已有的"改完复审"。
3. **循环出口**：`/sr-gdd-review` 只报告、不当场改；用户照报告裁决后再由 `sr-gdd-fix` 改的，**不再自动重审** —— 一次改动只自动触发一次复审，要再审由用户喊。
4. **落点四处**（权威一处，其余指针）：
   | 文件 | 改什么 |
   | --- | --- |
   | `sr-askme/references/gdd-pipeline.md` §三 §四 | **权威**：成稿不审 + 分级规则 + 循环出口 |
   | `sr-gdd-fix/SKILL.md` 第 2 / 5 步 + 产出规范 | 执行：第 2 步定档位、第 5 步按档位收口、产出规范加「改动后复核」的落点 |
   | `sr-gdd-review/SKILL.md` 分诊表 | 对齐：`active` 行写明"结构性改动后的必调复审"，`draft_gdd` 行指向 §三 |
   | `sr-gdd-human/SKILL.md` | 把"（**或直接编辑定稿**）"改成说明**后果**：不走 fix 就不触发那套复审 |

## Considered Options

- **每次改动都全量审**：✗ 不成比例，且会让报告贬值 —— 每次都跑，就没人再逐条读（联盟讨伐那 21 项被逐项裁决，正因为罕见）。
- **保持现状（用户喊才审）**：✗ 定稿改坏没有第二道网；而且 review 在用户可见处几乎不存在，"靠记得喊"不成立。
- **写进常驻 persona 兜底**：✗ 本轮不做 —— 定稿的实际改动入口只有 `sr-gdd-fix`（`sr-gdd-ai` 只管门内），跨 skill 兜底的必要性不足；按"唯一权威 + 指针"的纪律，多一处副本就多一处漂移面。**已如实记为待观察项**（见下）。
- **把成稿侧四项补进 `sr-gdd-human` 的自查**：△ 更省的替代，但**用户本轮未选**（他要的是"能被拦住的第三方复核"，而自查是作者自己核）。留作后续议题。
- **分级判据用"改了多大"**：✗ 无法核对。改用 `sr-gdd-fix` 第 2 步就产出的**改动清单**——它是可核对的中间物，事后能回答"这次为什么没审"。

## Consequences

- **结构性改动现在必过一遍全量复审**；轻量改动（改数值 / 文案）保持零额外成本 —— 这是本次分级的主要收益。
- **新产出落点**：轻量档会在**已有的**那份审查报告里追加「改动后复核」节。审查报告属过程档案、**不开历史版本**（`version-history.md` §一），这条此前已在 `sr-gdd-review` 里写死，本次沿用。
- **未做、待观察**（如实记，不当作已完成）：
  1. **常驻 persona 与 `使用说明.md` 都没动**。用户可见层至今**没有一处**告诉用户 review 存在（面板没列、human 的门不提、persona 不提）。若实践中发现"绕过 fix 直接编辑定稿"仍常发生，再考虑往 persona 加一句兜底。
  2. **成稿侧那四项**（D7 / D10 / §11 / 结果章留痕）仍无人自动核 —— 成稿门靠用户看。
- **验证**（可复跑）：`npm run check:bundled-skills`（正文 149,024 字节、11 条注册、与磁盘逐字一致）· `check:host-skills`（注册 11 条 / 模型可见 9 条）· `check:teaching`（快照无漂移）· `npm run lint`（exit 0）· `npm test`（**200 / 200**）。
