# ADR 0039 · sr-impl-check 的 UI 核对范围在开工时一次问清，收到图后不再回头

- 状态：已采纳（2026-11-20）
- 影响面：
  - `sr-workbench\skills\sr-impl-check\SKILL.md`（新增第 0.2 步；第 5 步改为条件执行；description；交付段第 5 条）
  - `sr-workbench\skills\sr-impl-check\references\ui-diff-guide.md`（第 2 步加"开工时做"、第 3 步去掉"报缺再开工"）

## 背景

旧流程把「要不要做 UI 核对」和「收图清单」都压在第 5 步，实测中造成两处空转：

1. 第 0 步只确认「核哪个包、哪份是定稿」，末尾那句是「代码核完还需要你提供 N 张实机截图，
   我**稍后**给清单」。用户一答应做 UI 核对，**手上没有任何可做的事** —— 清单还没到，只能等代码核完。
   这是用户实测后当场指出的问题（"为什么没有跟我要实际截图"）。
2. 用户把图放进来了，`ui-diff-guide.md` 第 3 步仍要求「先跑一遍核对，把缺的列出来**再开工**」，
   等于收到图之后还要多一次往返。

## 决定

1. **第 0 步拆两段**：0.1 要包与定稿（原样保留）；**0.2 必问一句「这轮做不做 UI 核对」**，只问一次，
   两个分支走到底、不来回改口。
2. **选「否」→ 整条链路不碰 UI**：跳过第 5 步，不建 `UI对照/`，报告不出「UI 外观偏差」一节，
   交付物只出需求清单 + 报告 + 对照页三件；之后任何环节不再提截图。
3. **选「是」→ 当场把收图清单交出去**：建 `UI对照/` + 按 `assets/ui-capture-checklist.md` 写
   `_收图说明.md` + **把配对表贴进回复正文**（只说"文件写好了"等于没给），然后立刻转去核代码 ——
   用户截图与代码核查并行。把清单留到第 5 步才给，是本 skill 最常犯的错。
4. **收到图 = 交付信号**：不再提问，一气做完 自验 → 逐屏比对 → 标注出图 → 写报告 → 出对照页。
   **缺图不阻塞交付**：缺的屏在报告「UI 外观偏差」里记一条「未收到截图 / 工程该屏打不开」，
   照常出全套产物；用户补图后重渲染即可（`extract-check-data` → 改 → 重渲染，slug 不变，
   勾选与备注不丢）。
5. **唯一保留的提问权**：定稿自相矛盾、只能由策划裁决的问题 —— 只问这一件，不夹带别的。

## 后果

- 开工阶段的提问从「1 件」变成「2 件」（包/定稿 + 是否做 UI 核对），但**总往返次数下降**：
  旧流程里"等清单"和"报缺图"两次往返被消掉。
- 选「否」的用户拿到的是纯代码验收交付，不会看到任何与截图相关的废话与空目录。
- 代价：0.2 每轮都要问，即便用户上一轮选过「否」也不能默认沿用 —— 每个包、每一轮单独确认。
