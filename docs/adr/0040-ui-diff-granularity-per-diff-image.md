# ADR 0040 · UI 对照按「逐张原图 + 一处一张 + 自检」执行，禁止用工具链压扁粒度

- 状态：已采纳（2026-11-20）
- 影响面：
  - `sr-workbench\skills\sr-impl-check\SKILL.md`（第 5 步重写为 5.1–5.6）
  - `sr-workbench\skills\sr-impl-check\references\ui-diff-guide.md`（第 4 / 5 / 6 步）

## 背景

sr-impl-check 固化之后，UI 对照的产出从「14 屏 35 处 + 35 张标注图」退化为「3 屏 5 条 + 5 张」。
回溯会话记录 `session-d09cfd65`（turn 1–2，即固化 skill 之前的那次原始任务），差异是明确的：

| 动作 | 那次（好） | 退化后 |
| --- | --- | --- |
| read_image | 41 次 | 约 20 次 |
| 看图方式 | 逐张原图 + 放大核对 | 拼接成对图看整体 |
| 标注图 | 35 张，一处一张 | 5 张，同类合并 |
| 出图工具 | 自写脚本，支持跨页组合与坐标校准 | 套用现成 `annotate-ui-diff.py` |
| 出图后自检 | 抽总览缩略图体检 35 张 | 无 |
| 上下文占用 | 25 万 / 100 万 = 25% | — |

三条排除结论：

1. **不是上下文不够** —— 那次只用了 100 万窗口的 25%，41 次读图毫无压力。
2. **不是 subagent 分工** —— 那次 UI 对照是单会话跑完的；5 个 subagent 属于后来 turn 4 的代码核查轮。
3. **不是策划模式** —— 两次 preset 的系统提示相差仅约 1.4k token。

真正的机制是：**skill 把「手写脚本、按每处差异定制」固化成了「往现成脚本里塞 JSON」**。
`regions` 结构一次表达不了二三十条，写起来麻烦，执行者就顺手合并 —— **工具的表达能力反过来压扁了产出粒度**。
`ui-diff-guide.md` 里那句「同类跨屏合并成一张图」是直接诱因。

## 决定

1. **四条原始约束写进 SKILL.md 第 5.1 节，逐条照做**：报与效果图不一致处 / 每张图只标一类 /
   效果图有而工程没有的也要说 / 代码生成内容不同属正常只看 UI 样式。
2. **本步基准是效果图，不是定稿**。定稿与效果图冲突的照样报，标注里注明「定稿口径不同，待裁决」。
   把「定稿优先」搬进这一步会主动吞掉差异。
3. **看图必须逐张读原图**：每屏读效果图 + 工程截图两张，屏数 × 2 是 read_image 最低次数；
   结构有疑点再放大读。**禁止用拼接图代替看原图**（拼接会压掉细节，拼接图只服务于出图）。
4. **出图一处一张**：14 屏 30–40 张属正常量级。「每张图只标一类问题」约束的是一张图不混标两类，
   不是「一类只能一张」。**禁止为出图省事合并条目**；脚本装不下就分批或另写批处理，不许减数量。
5. **出图后必做三项自检**：缩略图体检取歪、差异条数与图张数对账、抽样复读 2–3 张。

## 后果

- 「3 屏 5 张」这种退化形态在流程上被堵住：读图次数与图张数都有了可对账的下限指标。
- 代价：UI 对照阶段读图次数与出图张数显著上升，单次任务的 token 与耗时都比退化后高。
  这是用户明确要求的取舍 —— **要效果，不要省**。
- `ui-diff-guide.md` 保留了这次的历史教训注记，避免下次又把「一处一张」读成「一类一张」。
