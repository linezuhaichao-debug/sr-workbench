## 背景

联盟讨伐写回事件 `WB-20261016-001` 激活时事务失败并回滚。`prepare_writeback_event.py:1039`
（**激活后**复验）报 `writeback scope 校验未通过`——真因被 GBK 解码吞掉，实际是
`下游发布状态.last_published.package_dir hash mismatch`。

根因（读代码 + 现场比对确认）：激活事务的归档步骤是

```python
archive_target = formal.parent / "版本归档" / pkg_path.name   # 名字固定
_shutil.move(str(pkg_path), str(archive_target))
```

`版本归档/下游交付包_联盟讨伐` **事先已存在**（上一轮 v1.0.20261015.5 的包，未加后缀）。
`shutil.move` 遇到已存在的目标目录时会把源**嵌套**进去 ⇒ 归档目录里变成
「旧包 4 个 md + 新包整个目录」。随后激活后复验按 `dir_ref["path"]` 算树哈希，
算的是这个被污染的归档目录 ⇒ 与发布记录 `980c4936…` 不符 ⇒ 事务回滚。

回滚只做反向 move（`版本归档/…` → 当前包位），于是把「旧包内容 **+** 嵌套的新包」整体搬回
当前包位 ⇒ 当前包目录里出现 `下游交付包_联盟讨伐/下游交付包_联盟讨伐/` 双层结构，
其中外层是 v1.0.20261015.5、内层才是 v1.0.20261015.6。

该缺陷 **2026-10-13 已出现过一次**（当轮靠"事先把旧归档目录改名"规避，未修脚本）。本轮复发。

## 决定与修复

修复只做**状态还原**，不动任何语义产物；每一步都用树哈希证明，而不是"看起来对"：

1. 当前包重建：把内层（v1.0.20261015.6）提升为 `03_正式交付/下游交付包_联盟讨伐/`，
   树哈希 = **`980c4936…`** = 发布记录值；并与其 zip（sha `5b4ea27f…`）**逐文件一致**（17 文件全等）。
2. 旧包恢复：外层内容移到 `版本归档/下游交付包_联盟讨伐__归档件_08C3E4EB/`（目录名用该版正式版
   hash8，与既有 `__归档件_XXXX` 命名一致），树哈希 = **`3cf77c67…`** = 其 zip = 该版历史记录值。
3. 重跑激活成功；激活后 `--validation-scope writeback` = `PASS_WITH_WARNINGS`（0 ERROR）；
   归档目录树哈希与发布记录一致；可发送位已清空（旧包与 zip 都在 `版本归档/`）。

命名约定统一为：**归档目录一律 `<原包名>__归档件_<该版正式版SHA8>`**，
历史遗留的 `_v1.0_ue` / `_v1.0_official` 保持原样不改（不动历史）。

## 纪律

- **激活前先看归档位**：`版本归档/<包名>` 若已存在，先按上面约定改名，再激活；
  这是当前唯一安全的规避手法（不改脚本的前提下）。
- **遇到 `writeback scope 校验未通过` 但输出为空**：先按上面"真因被 GBK 吞掉"的经验，
  自己用 `validate_run_package.py --validation-scope writeback` 跑一遍拿真错误，不要按空消息猜。
- **回滚不等于还原**：反向 `shutil.move` 在目标位已被重建/未被清空时会产生嵌套。
  判断"回滚是否干净"必须**算树哈希**，不能只看文件在不在。
- 修复状态类问题时**只搬文件、不改内容**，并留下三个哈希（当前包、旧包、旧包 zip）作证据。
