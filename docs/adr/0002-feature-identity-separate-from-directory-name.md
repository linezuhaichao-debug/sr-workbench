# 功能身份与目录名分离（feature_id）

信息架构的地基是"目录 = 功能，零猜测"。但**改名是正常业务**：两份真实 UE 交付都附带改名（神话宝库 → 诸神降临；联盟悬赏 → 联盟讨伐），而工作区里**已经出现后果**——`features\神话宝库\`（38 个文件）与 `features\诸神降临\`（2 个文件）作为两个功能目录并存，`运行包_联盟悬赏` 与 `SR_联盟讨伐_交互交付物_*.zip` 同样并存。身份若等于目录名，改一次名就把一个功能裂成两个、并把历史切断；而"当前有效定稿"又需要判断"谁取代了谁"。

因此：**每个功能目录里放一份身份声明（`feature_id` / `name` / `aliases`），`feature_id` 终身不变；目录名只是标签。**

## Considered Options

- **把 id 写进每份产物的 frontmatter** —— 最贴合"不发明新数据格式"，但改名要改 N 处，且新产物忘写就掉队，同一功能的产物会漂移成多个身份。
- **只记一条改名记录** —— 零新格式，但任何"按 id 找东西"都要先走一遍改名记录链，代际越多越脆。

## Consequences

- 新增一份身份声明文件，**与 §4.6.3「台账不新增文件」的精神冲突**——这是显式承认的例外：台账是读法，身份是事实。
- "当前有效定稿"的判据从"猜文件名日期 + 主题"改为"按 feature_id + 日期排序"。
- 工作台的功能卡数量从"目录数"改为"feature_id 数"，改名不再虚增功能。
