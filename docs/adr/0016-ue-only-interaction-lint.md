# 0016 · UE 稿「只留交互」判据进 lint

> 触发：2026-10-13「圣物系统」出 UE 稿时，规则块把定稿 §5 的 UE 行**整句照搬**，于是 §4 / §6 的口径也跟着进了界面稿。
> 用户点名：「`保底提示：展示「再抽取 N 次，必出红色圣物」，次数按既有保底规则计算（圣物常量表.cycleGuaranteeCount / firstCycleGuaranteeCount）；不新增第二套保底` —— 这句话里逗号后面的都无关」。

## 背景

- **根因**：`content.json` 抽取（sr-gdd-ue 第 2 步）是"整句搬运"；而定稿 §5 的 UE 行本身会混着配置指代与规则口径 —— 那一行在定稿里是对的（定稿是设计 + 实现依据的综合产物），搬到 UE 稿里就成噪音。
- **三道关都没拦住**：`lint_content.py` 的越线词表只查"定稿 §6–§11 的整节内容"（表清单 / 字段表 / AC 编号 / 过程措辞），**没查行内混入的 `表名.字段名`**；渲染器只看字段与图片；冒烟只看版式。**30 处靠另写审计脚本才发现**。
- 影响面：13 块 / 107 块（12%）。

## 决定

1. **`lint_content.py` 的 `RED_LINES` 新增两条 FAIL 判据**：① **配置字段指代** —— `表名.字段名`、反引号包住的标识符；② **规则口径句** —— 不新增 / 不参与折算 / 不硬编码 / 不额外配置 / 与来源圣物的分类无关 / 不得重复计入 / 参考值 X，待定 / 待配表 / 万分比 / **按既有…规则计算**。
2. **抽取层口径写清**：UE 稿只留"这个界面长什么样、控件什么行为"；但**看着像技术、其实决定界面反应的照留**（失败不本地强制成功、跳过动画不改结算结果与奖励顺序、结果卡归类、属性侧别、状态以服务端返回为准）。
3. **文档与判据同步**：`references/content-schema.md` 的越线清单新增"行内混入的 §4 / §6 口径"一条（含上面的例外）。

## Considered Options

- **只在 schema 文档里加一句提醒**：✗ 文档提醒不拦人 —— 本次就是活证据。
- **在定稿侧把 §5 的 UE 行写干净**：✗ §5 属设计文档，字段对应在那里是必需的（D7 上游映射）；该筛的是抽取层。
- **判据进 lint（FAIL 而非 WARN）**：✓ 采纳 —— 这类内容对 UE 同事是纯噪音，命中即返工，不该降级成提醒。

## Consequences

- **反例验证（可复跑）**：把用户点名那句原样塞回 → **2 条 FAIL**（命中 `圣物常量表.cycleGuaranteeCount`、`按既有保底规则计算`、`不新增`），退出码 1；只保留口径句（去掉字段名）→ **1 条 FAIL**（命中 `按既有保底规则计算`）；清理后的正例 **0 失败 / 0 警告**，退出码 0。
- 该文件在 `SKILL.md` 的「上游依赖（只读，勿改）」清单里 —— 本次改动**经用户明确授权**；后续同类改动同样先授权。
- **判据的能力边界（如实记）**：词表级判据会漏掉不含上述词的"口径句"，仍需第 2 步人工核对 + 抽查；本次的审计脚本（`.tmp\圣物系统\audit_ue_content.py`，临时件）就是补这个缺口的办法，将来可考虑固化成工具的第二道扫描。

## 补（同日）：不止 UE 稿 —— **定稿 §5 本身就不该有配置字段**

用户追了一句：「我觉得这种情况出现在定稿里就不对」。核对判据后成立：

- **判据**：**D2 的定稿变体** —— 「配置对应**只写在 §4 的「配置字段」列与 §6 配置契约里**」；而 **§5 的 UE 表列名是「编号 | 规则（详细）」，没有「配置字段」列** ⇒ 字段名在 §5 无处安放。同理，系统级口径句（"不新增第二套保底"）属 §4，也不进 §5 —— **§5 是交互规则表**（D5）。
- **实情**：那 23 处字段引用**不是从成稿继承的** —— 成稿 §5 零配置指代（D2 成稿变体）；是**定稿整合那一步自己加的**（当时的做法："给关键行补字段引用"）✗。
- **处置**：定稿 §5 的 **13 行**改成只写交互（走 `/sr-gdd-fix`，留档 `圣物系统_定稿_20261013_3.md`）；UE 稿从清理后的定稿**重新派生**（源先干净、派生物后生成）。复核：§5 残留疑点 **0**、§4「配置字段」列 **63 处引用原样保留**、骨架与 UE 行数未变（H2 11 / H3 36 / `####` 0 / UE 80）。

### 两处判据缺口的处置（2026-10-13 用户裁定：只补 review）

1. **`sr-gdd-ai/SKILL.md` 的行内标注段**写「配置值不标 `[真实]` —— 数值以配置表为准、随时会改，正文只写 `表名.字段名` 指向它」，与 D2 的"只写在 §4 配置字段列与 §6"**在 §5 上冲突**。**用户裁定：不改** —— 该段讲的是数值出处口径，D2 在 §5 上优先；以后由人工在整合时盯住（本条留档即为此）。
2. **`sr-gdd-review/SKILL.md` 的 V4**：**已补**（2026-10-13）—— 判据写明两处都要扫：① §4 各规则的「细节」列；② **§5 全部界面的 UE 表**（UE 表没有配置字段列 ⇒ 字段名与系统级口径句在 §5 无处安放），并注明"只扫 §4 会漏（2026-10-13 实例）"。

判据 / 文档侧改动按分账纪律先经授权：本条的 review 改动**经用户明确授权**；ai skill 那条**用户选择不改**，故此 ADR 是它唯一的留档处。

## 补三（2026-10-13）：工具决定在功能账本里的复述已清除

`lint_content.py` 新增两条 FAIL 红线（配置字段指代 · 规则口径句）并用反例验证会红、`references/content-schema.md` 越线清单同步 —— 这段原本被复述进了「圣物系统」功能账本那条 UE 清理决策的**影响行**；按分账判据移除复述，功能账本只留指针。判据与验证记录以本 ADR 与 `content-schema.md` 为准。
