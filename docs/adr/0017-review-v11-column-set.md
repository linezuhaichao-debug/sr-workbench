# 0017 · skill 内容会滞后于仓库文件（会话/进程级快照）——以 V11 为例

> 触发：2026-10-15「圣物系统」定稿重跑后的全量复审。会话据读到的 `sr-gdd-review` V11 文本（旧的三列口径）报了「判据与九列模板冲突」，随后在盘上文件里看到的是**已同步的新口径**，一度把它当假问题撤回；**当日实验证明没有撤回的必要** —— 我读到的确实是旧文本，问题在 skill 内容快照，不在文件。

## 实验（决定性，可复现）

1. 盘上 `skills/sr-gdd-review/SKILL.md` 的 V11 已被本会话亲手改为新口径（指向 `feature-gdd.md` §7 声明的列集）—— 文件确定是新的。
2. **同一会话内再次调用 `skill(sr-gdd-review)`** → 返回的仍是**旧的三列判据**（`表头逐字等于 | 键 | 中文文案 | 状态 |（列数不同即不通过）`）。
3. ⇒ **本会话拿到的 skill 内容 = 快照，不随盘上文件变化。**

盘上复核：全盘只有一份物理 `SKILL.md`（仓库 1 份 + 软链到 profile 的 `node_modules/dsh-client-ui-sr-workbench/skills/` 4 条，内容一致、无旧串），旧串只出现在一份 15:29 的差距分析文档里（引文）。⇒ 旧文本**不在盘上**，只在会话读到的快照里。

## 结论与处置

1. **改 skill 后，本会话不生效** —— 要生效需**新会话**（若快照为会话级）或**重启应用 / 重载插件**（若为进程级）；两者未再区分（`开新会话读同一条判据`即可判定：新文本 ⇒ 会话级；仍旧文本 ⇒ 进程级）。
2. **纪律（本条的核心）**：凡"某文件里写着 X"的断言，**先 read/grep 那个文件**；**skill 加载内容与仓库文件不一致时以文件为准**，并把不一致本身当问题上报 —— 本功能那次的正确表述是「文件已同步 ✓、我读到的快照仍是旧版 ✗」，不是"我读错了"。
3. `sr-gdd-review` 的 V11 判据文本本身：文件侧已为新口径（八列基准 + 键名未核验时增列 `候选KeyName` 成九列），**无需再改**；本会话对它做的改写与文件原意等价。
