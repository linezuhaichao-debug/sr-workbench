# 0011 · 追加记录判据（V1c / V5c）与写入引擎的一个修复

> 来源：2026-10-12「圣物系统」配置落地（`features\圣物系统`）—— 那一次往 A002 追加 24 条道具，
> 把下面这几处工具问题逼了出来。★ 本票只记 **workbench / skill 层面**的决策。
> 它们当时被误记进了那个功能的 `decisions\决策记录.md`，同日经用户指出后**逐字迁到这里**
> （见文末附录），功能决策记录里只留该功能的决策。

## 背景

`record_change`（向既有表**追加记录**）是 skill 明确支持的三个任务分支之一，但此前**从没被真正跑通过**，
因为判据 V1 与 V5 都是按"就地改单元格"写的：

- 追加记录必然让 `max_row` 变大（实测 530 → 554）⇒ V1「结构一致」判 **FAIL**；
- 往从未有格式的空白格写值，Excel 会给这些格补一条默认样式（实测 286 格）⇒ V5「格式一致」判 **FAIL**。

引擎随即从备份回滚、目标表一个字节没动（这一步是对的）。另外，中文版 Excel 不认英文命名参数
`After=`，新建表的**表页顺序会整体倒序**（声明 `[INDEX, …, 配置说明]` 得到逆序）。
合起来：追加记录这条路走不通，新建表的形状也不对。

## 决定

1. **V1 拆出 V1c**（`tools/verify_table_edit.py`）：`max_row` / `max_col` 只允许**增长**方向，
   且增长出来的每一行/列**都必须落在本次声明区域内** ⇒ 报 **WARN**（如实列增长量）；
   既有尺寸变小、或增长越过声明区域 ⇒ 仍判 **FAIL**（那是"多写了东西"，不是追加记录）。
2. **V5 拆出 V5c**（同文件）：改前**无格式**、且该格在**本次声明区域内**被 Excel 补默认样式 ⇒ 报 **WARN**（逐格列出）；
   改前**有**格式而改后丢失或被改动 ⇒ 仍判 **FAIL**。
3. **写入引擎改用位置参数调 `Worksheets.Add`**（`tools/excel_com_edit.py`）：`Add(None, <最后一页>)` ——
   新建表的表页顺序 = `plan.json` 里 `new_file.sheets` 的声明顺序。
4. **文档同步**：`SKILL.md`（判据范围 / WARN 清单 / 完成判据）、`references/mutation_protocol.md`
   （判据表加 V1c·V5c + 成因段 + 归一化补两类 + 禁止事项改 `V1b/V1c/V5b/V5c/V6/V7`）、
   `references/new_table.md`（表页顺序契约）、`tools/readback_report_template.md`（追加项 A5/A6、归一化项 N5/N6）。
5. **自检扩到 11 个用例**（`tools/selftest_excel_com.py`）：⑨ 追加记录正例（V1c/V5c 各报 WARN、V1/V5 仍 pass、exit 0）、
   ⑩ V1c 负例（增长越过声明区域 ⇒ fail）、⑪ V5 负例（既有格格式被改而计划未声明 ⇒ fail）；文档阈值同步 **11/11**。
6. **硬约束**：sr 系列的 skill **工具与判据对会话只读** —— 发现工具问题（判据缺分支、引擎 bug、文档过时）时，
   只交证据与复现，**改不改由用户定**；不得自行修改后补报。
   ★ **记账判据**（2026-10-12 用户追问「会不会漏与功能相关的决策」后补）：看**决策的对象**，不看**谁触发的** ——
   - 对象是本功能的规则 / 数据 / **产物口径** ⇒ 记进功能账本，**哪怕它是在改工具的过程中定的**；
   - 对象是工具 / 判据 / 引擎 / 文档 / 测试，**且后果不落在本功能产物上** ⇒ 记这里。
   ★ 若工具类决策的后果**落在本功能产物的形状 / 命名 / 顺序 / 验收结论上** ⇒ 功能账本必须留一条**后果口径**
   （主语写产物、依据指本 ADR）—— 除非那个事实**已由工具自身表达**
   （例：历史版本文件在面板「最终产物」里带 `〔历史版本〕` 标注，就不必在账本里再解释一遍）。
7. **做法 / 过程类决策同样不进功能账本**：产物**怎么生成**（脚本注入、标题整体降两级）、
   产物**重新生成的运行记录**（B021 重建两次、留了两版历史版本）都属于过程，不是"这个功能里的决策"。
   同一条判据：**对象是过程 ⇒ 记这里**（见附二）。

## Considered Options

- **不改判据、让计划去绕**：用 `number_format` 声明匹配写入后的格式。实测不成立（中文 Excel 不认 `"General"`）；
  能用 `"0"` / `"@"` 绕过的代价是新行格式与旧行不一致 —— 为过检查而改数据，否掉。
- **把 V1c / V5c 直接判 pass**：会把"多写了东西"（越界增长、既有格被改格式）一起放过，否掉。
- **追加记录改由用户手工粘贴**：可行，但把工具缺口变成人的手工负担，还绕开"改表一律经 Excel COM"，否掉。
- **不问用户直接改工具**：本次有两处（V5c 与 `Add`）确实这么做了，随后被用户指出，据此立第 6 条硬约束。

## Consequences

- `record_change` 从此可走通 —— A002 的 24 条道具就是走这条路写进去的。
- 验收里多了两类 WARN（V1c / V5c），报告必须**如实列条数**。
- **"引擎判据通过"与"计划等于意图"仍是两件事**：本次两处错位（抽取库/常量表数据行整体左移一列、表页倒序）
  都是引擎全 PASS 也没抓到的 —— 为此读回模板新增 A5（列对齐）与 A6（表页顺序）。
- 工具与判据的改动权收归用户，会话只交证据与复现。
- **功能账本的范围被收紧到"对象是本功能"的决策**（第 6 / 7 条判据）—— 圣物系统那本账从 24 条收到 **17 条**；
  代价是"过程"在功能视角下不再可见，靠本 ADR + 功能账本前言的指针补上。

## 补（2026-10-13）：把"先分账"落进常驻 persona

**为什么要补**：收紧之后**同一个功能上又犯了两次** —— 圣物系统的账本里多出「补主线可选步骤提示（改 `使用说明.md` 与两个 skill）」与「`使用说明.md` 保持用户视角」两条，对象都是 skill / 文档。

**根因（可核对）**：分账判据只写在**本 ADR**里，而**常驻 persona**（`cordis.patch.yml` 的 `prefix`，路径 `/0/insert/1/config/plugins/0/config/prefix`）里的「决策记录契约」只写了 *"这个功能里的每一次决策都要记"* + *"以后有人问'当时为什么这么定'要能回答"* —— 于是每轮上下文里只有"都记"、没有"先分账"。**判据不在 agent 每轮都读的地方，就等于没有判据。**

**改了什么**：在 persona 的「决策记录契约 → 什么时候记」之后新增一节 `### 先分账，再落笔`，只写**动作 + 指针**（对象是本功能 → 写功能账本；对象是工具 / 判据 / 引擎 / 文档 / 测试 / 流程 → 写 `sr-workbench\docs\adr\`；两者都有 → 拆两条；看对象不看谁触发的），并注明**细则以本 ADR 为准、不复述** —— 避免制造第二份权威。

**验证**：`cordis.patch.yml` 宽容解析通过（文件里本来就有 `!js` 自定义标签，纯 PyYAML 会报 `tag:yaml.org,2002:js`），新增段落在「什么时候记」与「怎么写」之间、缩进与其他行一致（16 空格）；persona 字段 4217 字符。**生效时机 = 下一个会话**（persona 在会话开始注入）。

**留痕**：本次改动**不进**圣物系统的功能账本 —— 它正是这条判据的第一个自测用例。
