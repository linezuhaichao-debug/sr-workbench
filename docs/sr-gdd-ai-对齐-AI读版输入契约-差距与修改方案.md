## 0. 结论摘要

1. **"零"的准确含义不是"没有未决项"**，而是三条可判定的硬指标：
   - **零追问** = 零**未闭合 P0**（未闭合 P0 直接阻断候选稿曝光 / 审核签核 / 正式激活，`question-table.md:105`、`workflow.md:86-87`）。数值未定档、Key 未建、美术未出、UI 状态未定稿**都是合法的非阻塞边界**（`workflow.md:71-73`、`materials-and-images.md:37,47,69`）。
   - **零推断** = 不推断**缺失的执行语义**（`workflow.md:58`）。
   - **零开放项** = 定稿**每一个信息点都有处理状态**，8 类之一：写入正式规则 / 引用结构化源 / 标记待确认 / 标记后续补充 / 转下游确认 / 本版本不做 / 无关废弃 / 提出追问（实证判据见 `原文覆盖校验表_联盟讨伐.md:3`）。
2. **实测结论：这条路已经基本走通。** 联盟讨伐的初始转换**只产生 1 条追问**（Q-001），覆盖校验结论为"通过（无'影响执行语义且无处理状态'的信息点）"。**真正的差距集中在少数几类可枚举的点上**，不是系统性问题。
3. **那唯一 1 条 P0 的类型值得记住**：不是信息缺失，而是**两条各自正确的规则组合后产生未定义场景**（终极难度血量无限 × 残血提醒按百分比阈值）。这类"组合歧义"是定稿最难自查、下游最容易撞上的一类。
4. **追问重灾区是可见文本（多语言）**：写回阶段 5 条策划裁决里 4 条与 Key 有关（核验状态、占位值、界面文案完备性、历史候选键）。
5. **一个反向印证**：2026-10-15 的 §1/§2 改版（§1 只留一段"功能概述"、§2 换成"本功能不解决什么"）方向与下游裁决**完全一致**——策划已裁决过"AI 读版「功能概述」只保留定位段，删除「为什么做」「玩法张力」「玩家的稳定参与理由」「版本范围内的模块」「本功能不做」5 段"（`策划裁决台账_联盟讨伐.json` C-001）。

## 1. 下游契约对输入的要求（判据速查）

### 1.1 必须先问策划（P0 来源）——`no-fabrication.md:16-21`、`question-table.md:19`

- 核心规则不清：**入口、解锁、状态转换、消耗、奖励、结算、限制、公式、异常、范围外**。
- 文本 / 图 / 配置 / 多语言**冲突**且影响实现或测试。
- 多来源看似描述同一规则，但在**属性 / 效果 / 目标 / 条件 / 数值**上不一致。
- 关键规则**只出现在图里**且正式含义不清。
- 判断不了某改动是否属本版本。
- 要写正式规则但**缺明确来源**。

> **不得用"放入待确认清单"绕过未闭合 P0**（`question-table.md:109`）；兜底规则是"若不确定某缺口是否阻断正式交付，问策划"（`workflow.md:89`）。

### 1.2 允许写成非阻塞边界的情形

| 情形 | 出处 |
| --- | --- |
| 配置数值未定档（写字段用途 + 权威范围 + 限制即可） | `workflow.md:73`、`materials-and-images.md:37` |
| UI 状态未定稿 / Key 未建（标为后续回写项） | `workflow.md:73` |
| 多语言源路径未接入（不阻断、默认不问路径） | `materials-and-images.md:47` |
| 美术未出 / 图片状态不确定（写"证据/视觉参考"边界） | `materials-and-images.md:69` |
| 图片信息点可落安全状态（已承接 / 仅视觉参考 / 配置为权威 / 后续补充） | `materials-and-images.md:66` |
| 打点缺失 | 四文件**无追问规则**（只在 `materials-and-images.md:11` 列为可选输入） |
| 工程机制（RPC 名、字段名、刷新机制、代码归属） | `workflow.md:75`（**不问**；只写玩家可见结果） |

### 1.3 输出侧的硬性格式门（会 fail-closed 的地方）

- `多语言引用` 表头须含 `UI位置` / `UI状态` / `触发` / `用途` / `占位符`；状态词必须取自注册词汇表（`新增需求 / 修改需求 / 已提供Key-未核验 / 已核验Key / 新增Key候选 / 修改Key候选 / 建议复用 / 本功能不再引用 / 待分配Key / 待确认 / 不纳入AI读版`），**自造状态词告警**（`localization-coverage.md:131-136`）。
- **官方 Key 列只能放已核验官方 Key 或 `待分配Key`**；候选名必须单独列（`候选Key名` / `建议命名`）（`contracts-formal.md:78`）。无已核验权威源时**不得**声明 `已核验Key`（`localization-coverage.md:135`）。
- 占位符必须是**对象数组** `{token, meaning, source, optional}`，不是字符串（`localization-coverage.md:133`）。
- **AI 提议的新 Key 首字母必须小写**（`localization-coverage.md:136`）。
- `配置表引用` 必须给**字段用途**，不能只有表名 + 字段名（`contracts-formal.md:74`）。
- 核心对象/状态模型：功能有持久实体、槽位、品质、资源、进度、激活状态、队列、冷却、结算状态、跨系统依赖时**必须有**（`contracts-formal.md:68`）。
- 覆盖自查必须逐类留痕：可用/不可用、确认/取消、成功/失败、空/等待/冷却、奖励/消耗/结算、带占位符的数值/单位/数量/名称/时间（`localization-coverage.md:13-22`）——**消耗与获得必须成对写全**。

## 5. 不该做的（过度对齐反而有害）

1. **不要为"零开放项"把未定数值编出来**——违反 `no-fabrication.md` 与 sr-gdd-ai 的"宁可详尽标注待确认，不假装已定"。
2. **不要消除合法的临时边界**：下游契约明确允许配置数值/Key/UI 状态/美术处于临时态，只要写成边界（`workflow.md:71-73`）。
3. **不要在定稿里照抄 AI 读版的章节结构**（`核心对象与状态模型`/`资料权威范围` 等）——定稿是**输入**，AI 读版是**产物**；定稿加这些章节会破坏 sr 系列的模板契约（D12）。
4. **不要用生命周期标签冒充处理状态**（如"待策划确认中""本轮未处理"）——下游明确禁止（`localization-coverage.md:30`）。
5. **不要为了"减少追问"而删掉信息**：C-001 的教训是"重复信息"要减，但**执行语义一条都不能少**。

## 6. 验收判据（怎么证明"零"达成了）

转换前用这四条自查，等价于下游的覆盖校验：

1. **P0 自检**：把"入口 / 解锁 / 状态转换 / 消耗 / 奖励 / 结算 / 限制 / 公式 / 异常 / 范围外"十个面逐条过一遍，每个面要么有确定口径，要么显式标"本版本不做"——**不得有裸的"待确认"**。
2. **组合自检**：列出全部"特殊态"，与每条相关规则做交叉，确认交叉结果已写（A1）。
3. **覆盖自检**：把定稿的**每个信息点**归入 8 类处理状态之一；只要有 1 条归不进去，就会变成下游的追问或推断。
4. **文本自检**：§5 每处可见文案 ↔ §7 键双向对扫 0 缺口；§7 的键名核验状态、占位值标记、占位符 token 齐备（C1–C3、C6）。

> 达成后的预期：初始转换产出 `triage.conclusion = no_planner_decision_required`（台账仍会建，用于区分"查过且无需问"与"没处理"），直接进候选稿 → 审核版 → 正式读版，无需策划语义裁决。
